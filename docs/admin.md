# poe-price-tool — Admin

Reference for whoever runs the server: architecture, environment, the `/config` volume, routes, data sources and their limits, rate limits and bans, languages, sessions, the daemon's channel. The procedures — install and deploy, update, league start, reverse proxy, backup and restore, troubleshooting, the host updater — are in **[docs/runbooks.md](runbooks.md)**. For usage (access, hotkey setup) see the [README](../README.md). For how the Net-Worth tracker prices your stash (source routing, Faustus mechanics, corpse rules) see [docs/pricing-logic.md](pricing-logic.md).

## Architecture

Four parts — client daemon, backend, browser, and a set of always-on background jobs feeding the Net-Worth tracker:

```
[Clipboard watcher (client)]         [Backend (Docker, home server)]              [Browser tab]
 copy an item                         backend/v2/server.mjs                        • item cards + mod filter
 → you copy the item                  • serves pages + data                        • History page
 → the daemon reads it                • WS /events (per user room)                 • Net Worth page
 → POST /item ──────────────────────▶ • POST /item                                 • live C:D + reference bar
                                       • /daemon/* (the daemon's feed, heartbeat, buyer whispers, session key, value grid)
                                       • poe.ninja (C:D, reference prices)
                                       • PoE trade API via APT's RateLimiter ────▶ pathofexile.com/trade

[Net-Worth background jobs, 24/7]     • Stash API (POESESSID cookie) ──────────▶ pathofexile.com/character-window
 auto-refresher (one tab/tick)        • Faustus CDN (public, no auth) ─────────▶ web.poecdn.com/api/currency-exchange
 Faustus refresher (hourly)           • Corpse pricer (Trade API, background
 corpse pricer (budgeted/hour)          queue tier) ────────────────────────────▶ pathofexile.com/trade

[/config volume, persisted]           networth-store.json · faustus-store.json · corpse-store.json
```

- **Engine reuse:** APT's parser + trade layer (`renderer/`, MIT license, copyright Alexander Drozdov) run **headless** — bundled via esbuild into `backend/v2/engine.bundle.mjs` (no Electron). `ws` is the server's only runtime dependency; `pathofexile-dat` and its two dependencies are in the image for the language generator alone (see "Data auto-update").
- **Two engine instances, one network path** (`backend/v2/engine-instances.mjs`). The bundle keeps its item/stat database in module-level closures that `initData(lang)` reassigns, so **one instance can serve exactly one language**; a second language imports the bundle a second time under a different specifier, which gives Node a second module graph with its own closures. Two consequences:
  - **Both languages live in the same versioned snapshot directory.** `ready()` sets the data root *process-wide*, so two instances pointed at different roots would read each other's data, and the localized load path still reads `data/en/client_strings.js`: `data/de` sits **next to** `data/en`, never instead of it. Loads and reloads run strictly serially; a `Promise.all` over the two would be a race, not a speed-up.
  - **The second instance is handed out as a frozen object with exactly one key, `parseItem`.** Rate-limit state is per module graph: the second instance starts on the virgin default (1 request / 5 s) and knows nothing of the windows the primary has learned, while the shared queue and the ban gate only guard calls made through the primary. One stray `searchPreset` there is a ban path, so `searchPreset`, `bulkPriceItem` and `searchRaw` are *not reachable*. A test pins the key set (a function added later fails the build), and a test with a fetch spy around a complete parse verifies `parseItem` is network-free.
- **Multi-user:** cookie `ppt_user` (one user per person, from `POE_USERS`) → separate rooms; **one** shared trade queue via APT's RateLimiter. Three-tier priority: manual search > paste (`auto`) > background jobs (corpse pricer) — background work never blocks normal operation. The same cookie carries the client language, which decides the parse instance and the UI language — from `/config/user-langs.json` if the user has chosen one on the settings page, otherwise from `POE_USER_LANGS`.
- **Frontend:** static — `index.html` / `app.js` (price check), `networth.html` / `networth.js`, `history.html` / `history.js`, `settings.html` / `settings.js` (client language + sync credentials + admin area, the last including the runtime configuration form and the restart button). Served directly by the backend (no bundler). All user-visible text goes through `frontend/i18n.js`, one string table per language; a page learns its language from `GET /users` on load and follows a change over the `league-state` message (`shell.js` applies it, so every open tab of that user switches at once), never from `Accept-Language` — a player on a German client wants a German page on an English system too. A key missing from one table is a hard test failure.
- **Unrecognized mods:** the vendored APT stat DB can lag GGG (e.g. it lists 25 sibling "Socketed `<tag>` Gems" stats but not Physical). `backend/v2/trade-stats.mjs` resolves a mod it can't map against GGG's own public stat catalogue (`https://www.pathofexile.com/api/trade/data/stats`) and splices anything it can resolve back into the search as an active stat; anything still unresolved is shown read-only as "not searchable" rather than silently dropped. This is a **data** endpoint, not the trade search — it does not go through the shared search `RateLimiter` and cannot cause a search ban. Fetched lazily, at most once per 24h TTL, only when an item actually has unknown mods, with a 10min cooldown after a failed fetch; every failure degrades silently back to "unresolved".
  **For a non-English client the line takes one detour first.** The catalogue is English, so `backend/v2/mod-text-pairs.mjs` brings the line to its English form through `data/de/text-pairs.ndjson`, a by-product of the language generator that covers *every* German description line of the current patch, not just the ones in the data set (going through the data set would be circular: an unresolved line is one it does not know); only that English form is looked up. The table is read lazily, per language, out of the active snapshot and dropped whenever a new snapshot is adopted, so table and data set are always from the same generator run; an English-only installation never reads it. **A line that maps to more than one English text resolves to nothing** — it stays read-only and lands in the gap view, because a confident wrong price costs more than a missing one. Same outcome when the patch is newer than the last generator run and the line is not in the table either, as on English when data set *and* catalogue both miss.
- **Client daemon:** `poe-price-daemon` (per machine) **polls the clipboard** — on a new value it runs `daemon/poe-price-post.sh`, which filters for PoE items, de-dupes, and POSTs. Polling (not `wl-paste --watch`) because XWayland game copies don't reliably fire change events. No key injection: you bind your key to PoE's own Ctrl+Alt+C copy. Chat macros (F5–F9) still run via evdev + ydotool. Details in the README.

### Routes and endpoints

Everything is on the one port; message and payload shapes are in [PROTOCOL.md](../backend/v2/frontend/PROTOCOL.md). *user* = the `ppt_user` cookie, freely settable (routing, not authentication); *admin* = the `X-Admin-Password` header, checked on every request ([The admin password](#the-admin-password)); *daemon* = the `X-PPT-Daemon` and `X-User` headers.

|---|---|---|---|
| `/`, the pages and their files | GET | — | static frontend (Price Check, Net Worth, History, Settings) |
| `/events` | WebSocket | user | the user's room: cards, prices, status lines |
| `/health` | GET | — | `ok` |
| `/users` | GET | — | user list, app name, language per user |
| `/leagues` | GET | — | league list (poe.ninja, cached) and the active league |

| `/daemon/events`, `/daemon/stash-grid` · `/daemon/heartbeat`, `/daemon/whisper`, `/daemon/session` | GET · POST | daemon | the daemon's channel ([The daemon's back channel](#the-daemons-back-channel), [Value grid](#value-grid)) |

## Deploy

The backend runs as **one** container, reachable directly on its port (8788 in `docker-compose.yml`) or behind a reverse proxy, then with **websockets enabled**: the browser tab holds a WS connection on `/events`, and a proxy that does not pass it leaves the UI unconnected. **LAN-only, no auth — do not expose to the internet.** The stores persist in the `/config` volume; the user list comes from `POE_USERS`. Build, verify and reverse proxy: [runbooks.md → Install and deploy](runbooks.md#install-and-deploy) and [Reverse proxy](runbooks.md#reverse-proxy-npm-optional).

> The examples in these two files are from a concrete Unraid homelab, with its own paths (`/mnt/user/appdata/…`) and internal LAN address (`192.168.178.29`, e.g. `http://192.168.178.29:8788/`). The general approach (one Docker container, directly on its port or behind a reverse proxy with websockets) is what matters; adjust paths and addresses to your own environment.

### Background load (runs 24/7, whether or not anyone has a tab open)

Three background jobs poll continuously, independent of any open browser tab — worth knowing on a shared or metered connection. Three lighter ones run beside them.

- **Corpse pricer** — up to `POE_CORPSE_BUDGET_PER_HOUR` (default 25) anonymous trade searches/hour, budgeted and capped.
- **Faustus refresher** — one pass every `POE_FAUSTUS_REFRESH_MS` (default 1h) over GGG's public Currency Exchange feed; a pass walks back up to `POE_FAUSTUS_UNION_HOURS` (default 8) completed hours, one file each: on the order of **~200 CDN reads/day**. No session cookie and no trade API — a public CDN and a budget of its own, separate from the trade searches and the stash reads.
- **Net-Worth auto-refresher** — one step per tick (default 30s) ≈ **~2,880 steps/day in TOTAL**, using the configured users' live session cookies. **Not a per-user rate:** one refresher, one request in flight at a time, users walked round-robin, so a second user halves how often each user's turn comes round instead of adding a stream. One user gets ~2,880 reads/day and revisits a ~115-tab account roughly hourly; with three users it is still ~2,880 reads/day in total and each tab is revisited roughly every three hours. **A step is one request**, folder tabs included. A **folder tab** (Unique/Map stash) costs `1 + N` requests, because its items live in sub-folders on a different endpoint — 1+18 for the unique stash and 1+43 for the map stash on the account they were measured on (2026-08-19; the map stash had about 30 sub-tabs when first measured on 2026-08-11) — so it is `1 + N` *steps*, one sub-tab per tick; two folder tabs per lap put the daily *request* count a few percent above a lap of ordinary tabs. Those requests are **spread at the pace GGG's own published limits allow** (see "The pace between two stash requests"), over their own ticks, so a folder tab does not stop every other tab and user for its walk; spreading them does not change the request count. The ordinary one-request step is unaffected: 30 s between ticks is already slower than the derived spacing.

The three lighter jobs:

- **poe.ninja** — Chaos:Divine ratio and the reference rail, refreshed every `POE_CD_REFRESH_MS` (default and minimum 15 minutes) for each league in use; no cookie. While Net Worth is valuing, its merged exchange map reads 14 poe.ninja overview types at most once per `POE_NINJA_MAP_TTL_MS` (default 1 h, so up to 14 requests an hour). An empty map (a league start with no trade yet) or one where a type did not load is not kept, so it is rebuilt on the next valuation; each type is then asked again every 15 minutes, up to 56 requests an hour while Net Worth is valuing. After a failed attempt — a network error, a 5xx, an answer of the wrong shape, no answer within 15 s — the same type is not asked again for 15 minutes, and the last good answer is served meanwhile, but only up to `POE_NINJA_MAX_AGE_MS` (default 24 h) after poe.ninja gave it. Lookups of a type whose request is still running wait for it instead of sending their own.
- **Data check** — once a day (`POE_DATA_REFRESH_MS`) the item/stat data and the base-name list are compared with their sources by conditional request, so an unchanged day transfers almost nothing (see "Data auto-update").
- **Release check** — once a day, one request to `api.github.com` asking for the latest release of this tool (`POE_RELEASE_CHECK_DISABLED=1` turns it off).

None of this backs off when the tool is unused. The one exception is the net-worth auto-refresher, and only with hotkey daemons new enough to report the game: while no player's game runs, only every `POE_NETWORTH_IDLE_EVERY`-th tick reads a tab (one tab every 5 minutes at the defaults), and none with `POE_NETWORTH_IDLE_REST=1` (see "Sync follows the game" under "Net-Worth-Tracker"). It never reads more than without them.

What all three *do* back off for is a ban: while the global trade ban gate is up the corpse pricer is held with the rest of the queue, and the net-worth refresher stops with it (see "Rate limiting & bans"). The dials above have floors: the settings page cannot ask more often than every 30 seconds, whatever is typed into it (see "Configuration from the admin area").

### Rate limiting & bans

All trade-API traffic (price check, corpse pricer) shares one queue and one ban detector, `backend/v2/rate-limit-signal.mjs`, so the wording is recognised in one place. Separately maintained copies once drifted apart: the background crawler of the Cluster Crafter (about one trade search every 30 s, since removed) read a real GGG ban as a harmless local error and kept firing into it, which ended in two real trade-API bans during development.

`classifyRateLimit(err)` returns `{ seconds, kind }`:

- **`client`** — APT's own local backpressure ("Retry after N seconds"), thrown *before* any request leaves the app. Usually pure pacing: a short wait stays quiet and causes only a local backoff. From `CLIENT_GATE_MIN_SEC` (300s) upwards it DOES raise the gate — a client-side wait that long means GGG's headers taught the limiter about a real ban ("Retry after 13283 seconds" was reported as `client`, and treating that as pacing kept the app hammering).
- **`server`** — GGG's real 429 ("Please wait N seconds…" / "rate limit exceeded" / plain 429). A request hit GGG and was rejected.
- **`block`** — a 403 soft-ban, a Cloudflare/WAF HTML challenge, or a JSON-parse failure (the engine hides the HTTP status, so the message itself is sniffed).

`server` and `block` always raise the **global ban gate**, `client` from 300s up: while a real ban is active, `pump()` holds the *entire* queue — price-check, paste and background jobs alike — so the app can't extend the ban by firing more requests into it. An unref'd timer resumes the queue the moment the ban's `Retry-After` expires. The browser shows an amber banner with a live countdown; the Search button is blocked while it's up (so a user can't stack duplicate jobs behind the gate that all fire the instant it lifts).

**The gate stops the net-worth refresher as well**, although that path uses a different endpoint and a different credential: **a GGG ban on this deployment applied to the whole address rather than to an account** — it was ended by taking a new address, the alternative being roughly twelve hours — and a ban aimed at an address does not care which cookie the next request carries. The price is paid knowingly: the net worth freezes for the length of the ban and the history series gets a gap, which heals when the ban lifts; a ban costs every user of the deployment at once. `docs/bugs.md` B14 carries the full argument, including the direction that is deliberately *not* coupled: a stash 429 does **not** hold the trade queue, because a full window on one rule group says nothing about another rule group's window, even when both are keyed to the same address.

#### The stash path has its own budget — and its own answer to a 429

The net-worth refresher spends a different budget on different endpoints (`character-window/get-stash-items` and `/api/stash/…`), authenticated with a POESESSID rather than anonymous, with its own rules:

- **A 429 costs exactly one request.** `stash-client.mjs` does not retry it: the first 429 goes straight to the refresher, whose cooldown does the waiting — `POE_NETWORTH_COOLDOWN_MS` (default 10min) or the `Retry-After` GGG named, whichever is **longer**, never shorter.
- **A pacing wait longer than 90s is not slept out either.** When the headers say a window is nearly full, the client normally slows down (4× the base pace, or the rest of the window). Past 90s it stops instead of truncating the wait and sending anyway, and hands the wait to the same cooldown — so no request goes into a window GGG's own headers call full.
- **A 429 pauses every configured user, not just the one who got it.** The rule names below show that `Ip 45/60s` and `Ip 180/1800s` are part of the same budget, so a full window really is everybody's. The refused user sees "rate-limited by GGG", everyone else "another user was rate-limited — syncing pauses for everyone until …". The other user is never named.
- **A trade ban stops this path too** (see above and `docs/bugs.md` B14), with its own status text: "the GGG trade API has blocked this app — stash syncing pauses with it until …" (different causes, different remedies: a stash 429 is about this deployment's stash reads, a trade ban is waited out). A stash 429 leaves the trade queue running, deliberately.

Once per process, the first stash response logs which rules GGG measures this budget by:

```
[stash-client] GGG rate-limit rules for the stash endpoints (policy backend-item-request-limit): Account 30/60s ban 60s, Account 100/1800s ban 600s, Ip 45/60s ban 120s, Ip 180/1800s ban 600s — the rule NAME says what the budget belongs to (Ip = shared with everything else from this address, Account = this session) — derived minimum spacing between two stash requests: 24.8s
```

It is pure observation (headers that arrived anyway, no extra request) and repeats only if GGG publishes a *different* rule set — which the two stash endpoints do: the newer `/api/stash/…` one answers with `Account 15/10s ban 60s, Account 30/300s ban 300s`, so there are normally two lines per process.

#### The pace between two stash requests

**The pace is derived from the measured rules**, because a fixed 1500 ms is too fast for them:

- 1500 ms is **40 requests a minute**. `Ip 45/60s` is the tightest short window, so it would run at **89 %** of a limit whose only brake (`delayFor`) opens at 80 % and is *reactive*: it reads a state counter off a response, by which time the requests it reacts to are already out.
- The **long windows** count too. `Ip 180/1800s` is 6 requests a minute averaged over half an hour, `Account 100/1800s` is 3.3. The ordinary cadence fits (one step per 30 s = 60 requests per 1800 s), a **folder tab** as a burst does not: the map stash was measured on 2026-08-11 at 30 sub-tabs = **31 requests in 46 s**.
- That is **over a published limit outright**: a folder tab is walked on the newer `/api/stash/…` endpoint, whose own rule set is `Account 15/10s` and `Account 30/300s`, and 31 requests inside 46 s is past `30/300s` on its own; the unique stash adds 19 more on the next turn.
- Against the *first* endpoint's windows it is a violation only under the conservative reading: on an 18-tab account the round-robin reaches both folder tabs about three times per half hour, ~214 requests per 1800 s. Only ~52 of those go to the first endpoint, so its `Account 100/1800s` is safe if the two rule sets count separately, and the whole 214 is past `Ip 180/1800s` if they do not. The headers do not say which, and the one ban this deployment has an operator's account of reached the whole address.

So `backend/v2/networth/stash-pacer.mjs` derives the spacing. Every rule states a mean rate — `hits` per `windowSec` is one request every `windowSec/hits` seconds — and the strictest one wins, after the share this tool allows itself:

```
spacing = max( 1500 ms , max over all published rules of  (windowSec + bucketSec) × 1000 / (hits × share) )
```

- **All rules are honoured at once**, both windows and both endpoint groups. A response replaces the rule set of **its own policy** and leaves every other policy standing: a folder tab is walked entirely on the second endpoint, whose rules do not mention the 1800 s windows the walk is at risk of filling. See "A rule set GGG has withdrawn stops counting" for why that is keyed on the policy.
- **The share is `POE_STASH_IP_BUDGET_SHARE` (0.5) or `POE_STASH_ACCOUNT_BUDGET_SHARE` (0.75)**, by rule name — an address is shared with traffic this tool cannot see, a session is not. An unknown rule name is treated as `Ip`. On the measured set the binding rule is `Account 100/1800s`: against a window of 1800 s **plus its one-minute bucket** that is 18.6 s a request, of which the tool takes three quarters → **24.8 s**.
- **`bucketSec` is the window's RESOLUTION, and it is in no header.** GGG sums requests in buckets — 5 s on the short limit, one minute on the sustained one — so a published `45 per 60s` really covers 60–65 s of wall clock, and the rate is derived against the longer reading (source: `POE_STASH_BUCKET_SHORT_SEC` in the table). It costs 3.3 % on the measured set and can only ever lengthen a gap.
- **1500 ms is the floor and the fallback.** Before any response has been seen — the first request after a start — it *is* the pace, and no rule set and no share can derive anything shorter, so the stash path never sends faster than one request per 1500 ms, in any constellation.
- **The state is process-wide, not per client.** The server builds a fresh stash client every tick; the pacer survives it, because an `Ip` budget belongs to the address (shared across configured users) and a 1800 s window outlives any number of 30 s ticks. The reactive brake survives a tick with it, so a nearly-full window gets no free first request at the start of the next one.

At 24.8 s the ordinary cadence never waits (30 s between ticks already covers it). A folder tab with 30 sub-tabs (the measurement of 2026-08-11) takes **~13 minutes** for its 31 requests (at a flat 1500 ms they went out in ~46 seconds), one tick each, so nothing else stops meanwhile (see "Background load" and "When the refresher goes quiet"). Sequentially, the whole process cannot exceed 72 requests per 1800 s: 40 % of `Ip 180/1800s`, 5.4 % of `Ip 45/60s`, and 73 % of the account window — the share, by construction. Nothing sends an extra request to learn a rule: the limits are in the responses that arrive anyway.

#### A rule set GGG has withdrawn stops counting

**GGG varies the rule set, in both directions.** Over two days, one account on one address was answered with three different sets:

```
12.08. 14:12 UTC   Account 30/60s ban 60s, Account 100/1800s ban 600s,
                   Ip 45/60s ban 120s,     Ip 180/1800s ban 600s       -> 24.8 s
12.08. 14:13 UTC   Account 15/10s ban 60s, Account 30/300s ban 300s    (the folder endpoint)
13.08. 02:15 UTC   Ip 30/60s ban 120s, Ip 90/1800s ban 600s,
                   Ip 180/7200s ban 3600s                              -> 80.7 s
13.08. 11:28 UTC   the 14:12 set again                                 -> still 80.7 s
```

The 80.7 s at 11:28 is what a rule table that never removed anything derived from the strict 02:15 set (`docs/bugs.md`, B16). The table is keyed on GGG's policy (below), so a set GGG withdraws stops counting on the next response of its policy.

**The 02:15 set is not a punishment — it is a dead session.** The legacy stash endpoint answers the *same* policy in two forms: `Account,Ip` when the POESESSID was accepted, and `Ip`-only when it was not, with the address limit roughly halved in the second. The `gerwaric/acquisition` project measured exactly that on the same endpoint on 28.07.2026, and a GGG web developer described the mechanism in the official forum in 2018 — with a session id the budget is counted per account, and the IP limit is then twice as generous. The two forms here, digit for digit:

| rule | authenticated (11:28) | 02:15 | factor |
|---|---|---|---|
| `Ip` / 60 s | 45 | 30 | 1.5× |
| `Ip` / 1800 s | 180 | 90 | **exactly 2×** |
| `Account` rules | present | **absent** | — |
| a 7200 s window | — | 180, ban 3600 | only unauthenticated |

02:15 UTC is a night-time round with an expired cookie nobody was awake to notice. **So the change of form is an alarm, not a reason to slow down** (see "The rule names are also a session check"). Pacing still honours the `Ip`-only limits while they are what GGG published — that request really was measured against them — and lets go of them afterwards.

**Nothing here has been tightened on suspicion.** The authenticated set is digit for digit what a third party measured on 18.07.2026 from another account, another address and another continent — what GGG ships to everybody. GGG's penalties are binary (a timed lock, a withdrawn credential, a Cloudflare block); a quietly smaller set of numbers is not one of them.

**The key is GGG's own `X-Rate-Limit-Policy` header**, which names the budget a set belongs to. GGG's documented meaning: *"Policies may be the same across different API endpoints but are treated the same for rate limiting purposes."* Same policy name, one shared counter; different names, independent counters. It is part of the key, so a response is the whole truth about *its* budget and about nothing else: the folder endpoint's set can be restated thirty-one times during a walk without touching the ordinary endpoint's 1800 s windows, and a rule GGG has stopped publishing stops counting on the next response. Getting **faster** is therefore only ever GGG's decision, never a lapse of memory.

Two fallbacks, both in the conservative direction:

- **A response with no policy header replaces nothing.** It is added to the union: a missing header must not make two endpoints look like one budget and take a window away from a walk.
- **A rule expires if it is not re-published for `POE_STASH_RULE_TTL_MS`** (6 h), which covers a policy that is never asked again. The floor under that setting is 2 h, the longest window ever seen here, because a request can still be counted inside a window for as long as the window is; each rule is kept for at least its own window whatever the setting says. **A rule set that keeps arriving never expires**, however long the process runs.

The rule-set log line names the policy, because two sets with the same rule *names* could not be told apart otherwise — and whether a changed set restates the same budget or stands next to it is the whole question:

```
[stash-client] GGG rate-limit rules for the stash endpoints (policy backend-item-request-limit): Ip 30/60s ban 120s, Ip 90/1800s ban 600s, Ip 180/7200s ban 3600s — the rule NAME says what the budget belongs to (…) — derived minimum spacing between two stash requests: 80.7s
```

#### The rule names are also a session check

The `Account` rules disappearing from a policy that had them means the request was **not authenticated** (table above). The tool says so, once per change of state and in both directions:

```
[stash-client] the stash session is NOT being counted per account any more (policy backend-item-request-limit): GGG published only Ip rules, which is the form it answers an unauthenticated request with — the POESESSID is expired or was not accepted. Renew it in networth-users.json. The Ip-only limits are stricter, so the pace lengthens with them; that is a symptom, not the problem
[stash-client] the stash session is being counted per account again (policy backend-item-request-limit) — the POESESSID is being accepted
```

It is **observation only** — it sends nothing, changes no pacing and throws nothing. An unauthenticated request cannot read a private stash, so it is refused, and the refusal already travels the auth path: `401`/`403` → the refresher pauses *that user*, logs `cookie expired for <user> — renew it on the settings page (Sync settings) or in networth-users.json` and reports `state: "expired"` for them in the status line. A second pause on a header signal that is process-wide and cannot name a user would be wrong, and a false positive would freeze a healthy refresher until somebody edited a cookie.

A policy that has *never* published `Account` rules says nothing: only the transition is evidence. The check is per policy, so the folder endpoint and the ordinary one cannot accuse each other of losing a scope.

### Reading the log after a rate limit

Two things make a rate-limit banner explainable after the fact; both are pure observation and send no extra request:

- **Timestamps.** Every log line starts with `2026-07-31T14:03:21Z` (UTC, to the second), installed centrally in `backend/v2/log-timestamps.mjs`, so a banner can be matched against the requests that caused it, or told apart from the tail of an older window.
- **Consumer bookkeeping** (`backend/v2/trade-audit.mjs`). Every response from `/api/trade/*` is attributed to the consumer that triggered it — `price-check`, `corpse-pricer`, `data-refresher`, `stat-catalogue` — via an AsyncLocalStorage tag set where the request is dispatched, so no caller signature changed. It logs **two** kinds of line and no others:

  ```
  [trade-audit] rate limit 80% reached — consumer=price-check policy=search rule=Ip 8/10 in 10s (ban 60s if exceeded)
  [trade-audit] 429 from GGG — consumer=price-check policy=search rule=Ip 15/15 window=60s wait=300s; own requests in that window: corpse-pricer=4 price-check=2 (total 6) — this app only, other traffic from this IP (e.g. the trade site in a browser) is not counted
  ```

  The threshold line is **edge-triggered** per rule+window: one line when a window first gets tight, nothing again until it has fallen back below.

The counts are ours alone. Trade searches go out **anonymously**, so GGG limits them **per IP**, and the container shares its public address with everything else in the household, the user's own browser on `pathofexile.com/trade` included, which cannot be seen from here. A *small* number next to a 429 is therefore the useful answer: the load was not ours, and there is nothing to hunt for inside the app.

### What's in the image

Multi-stage build (`Dockerfile` in the repo root):

- **build** (`node:24`): installs the root deps (`ws`, plus the `esbuild` devDependency that does the bundling) and the renderer deps (`fnv1a`, for the search indices), builds the self-contained engine bundle (`node backend/v2/build.mjs` → `engine.bundle.mjs`) and generates the search indices (`*.index.bin`, gitignored → generated here).
- **runtime** (`node:24-slim`): only what's needed at runtime — `node_modules/ws`, `backend/v2/{server.mjs, engine.bundle.mjs, frontend/, data-refresher.mjs, apt-index.mjs, …}` and `renderer/public/data`. The data auto-update regenerates the search indices at runtime via `apt-index.mjs` (pure Node, no `renderer/node_modules` in the image). The path relation `backend/v2/` ↔ `renderer/public/data` is preserved (the default data path in `engine.mts` is relative). The server process runs as UID 1000; PID 1 starts as root and drops to it (see "How the container handles /config permissions"). Every `*.test.mjs` under `backend/` is deleted from the image (tests live in the repository, and the ones under `frontend/` would otherwise be served over HTTP).
- **health check**: `GET /health` every 30 s with a 5 s timeout, a 45 s start period (the server warms its caches on boot) and 3 retries before the container is reported unhealthy.

The images pin Node 24; `package.json` declares `engines` `node >=22` for running the server or the tests outside Docker (Node 20 reached end of life on 2026-04-30). The image additionally carries `pathofexile-dat` (with `pathofexile-dat-schema` and `ooz-wasm`, ~600 KB together) because the language generator spawns its CLI to export GGG's game data — dead weight on an English-only install, and without it a German install's generation run fails on a deployed container.

> **Files directly under `backend/v2/` are copied one by one.** A module added to the server's import graph but not to the Dockerfile makes the container crash on boot with `ERR_MODULE_NOT_FOUND`, and the test suite cannot see it, because it runs against the source tree. `backend/v2/dockerfile-closure.test.mjs` walks the real import graph and fails when a file in it has no `COPY` line, plus the two things the graph walk cannot see: `lang-pseudo-matchers.json` (read, not imported) and `pathofexile-dat` (resolved at call time).

### How a number in this table is read

Every numeric setting above goes through one reader (`backend/v2/env-number.mjs`, with the table of defaults and ranges in `numeric-settings.mjs`), with one rule:

- **Unset, empty or whitespace** means "not configured" and quietly uses the default in the table. An empty compose line must not switch anything off.
- **A usable value** is used as given.
- **A value that cannot be honoured** — a typo, a negative number, something outside the stated range, or a `0` on a setting that has no meaning for one — is **reported in the log, and the default is used**. It is never silently replaced, and it never stops the container from starting: for the settings that decide request volume the default is the conservative direction anyway (see the four exceptions below), and a boot loop would leave no admin area to correct the setting from. The line names the variable, the value, the reason and what is used instead:

  ```
  [config] POE_NETWORTH_COOLDOWN_MS=0 is not a usable value (zero is not a
  setting here; allowed: numbers >= 600000) — using 600000 instead.
  ```

  **What it falls back to is the DEFAULT, not the nearest allowed value**, so expect a jump rather than a nudge: `POE_CORPSE_TTL_MS=1800000` (30 min) runs on six hours, not on the one-hour minimum, and `POE_CORPSE_BUDGET_PER_HOUR=50` runs on 25, not on the ceiling of 30. The number actually in use is always in the log line — read that, not the compose file.

  **Four settings fall back to MORE traffic than the value that was refused.** Three because their dangerous direction is up: `POE_CORPSE_BUDGET_PER_HOUR` (a typo like `0.5` or `none` lands on 25 Trade-API queries an hour — a plain `0` is honoured and really does mean none), `POE_FAUSTUS_UNION_HOURS` (a refused value lands on 8, i.e. one hourly CDN digest fetched per unioned hour) and `POE_MAX_REQUEUE_ON_RECONNECT` (a refused value lands on 10 `auto` Trade-API searches per reconnect; a plain `0` is honoured and re-queues nothing). The fourth is `POE_NETWORTH_IDLE_EVERY`, through its ceiling: a value above 1000 lands on 10, so players whose game is not running get more stash reads than asked for, though never more than without game detection. All four say so in the log, and no other setting read through this reader answers a refusal with more requests to somebody else's server than were asked for.

- **The eight request-volume settings have floors, and the one budget a ceiling.** `POE_NETWORTH_SYNC_INTERVAL_MS`, `POE_NETWORTH_COOLDOWN_MS`, `POE_CORPSE_INTERVAL_MS`, `POE_CORPSE_TTL_MS`, `POE_FAUSTUS_REFRESH_MS`, `POE_CD_REFRESH_MS`, `POE_NINJA_MAP_TTL_MS` and `POE_DATA_REFRESH_MS` refuse anything below the minimum named in their row; `POE_CORPSE_BUDGET_PER_HOUR` refuses anything above 30. Each number is argued in its row, and at length in the range note at the top of `numeric-settings.mjs`. The reason is the ban that couples the two paths (see "Rate limiting & bans"): if a ban reaches the whole address, no path here has a request volume that is somebody else's problem. **An existing installation cannot break on this:** an out-of-range compose value takes the path above — one loud `[config]` line, the **default** is used, the container starts, the admin area still answers — and the log after the next `docker compose up -d` names it.

- **`0` is decided per setting, and the table says which it is.** It is honoured where it means something an operator needs to be able to say — `POE_CORPSE_BUDGET_PER_HOUR=0` ("query nothing"), `PORT=0` ("any free port"), `POE_LANG_SKEW_WARN_RATIO=0` ("warn on any gap"), `POE_MAX_REQUEUE_ON_RECONNECT=0` ("re-queue nothing"), `POE_TRADE_AUDIT_THRESHOLD=0`, `POE_NETWORTH_SLOW_STEP_MS=0`, the three display thresholds of the ask-conflict marker (`POE_ASK_CONFLICT_ABS_GAP_C`, `POE_MIN_ASK_EVIDENCE`, `POE_MIN_CONFLICT_HEADLINE_C`), `POE_RATE_LIMIT_BANNER_MIN_SEC=0`, all four `POE_NETWORTH_GUARD_*` bars, of which `POE_NETWORTH_GUARD_ARRIVAL_MIN_DIVINE=0` switches the arrival bar off, and `POE_NETWORTH_GUARD_STATE_MAX_NAMES=0` (keep no remembered price), `POE_NINJA_FAIL_LOG_MS=0` (log every failed poe.ninja attempt), `POE_LANG_MAX_COVERAGE_LOSS_RATIO=0` (the strictest bar, not an off switch), the two Net-Worth marker bars `POE_NETWORTH_THIN_TURNOVER_C=0` and `POE_NETWORTH_CORPSE_MIN_LISTINGS=0` (mark nothing), `POE_SESSION_RATE_MIN_MS=0` (every farm session gets a loot-per-hour figure) and `POE_SESSION_TOP_N=0` (name no biggest additions or removals). It is refused where it would mean a loop with no pause against GGG or poe.ninja, a cache that never holds anything, a backoff of no length, a stash request timeout that expires before any answer, a room that evicts every card as fast as it is created, or a marker that fires on everything.

No setting with a default is read through `Number(x) || default` (which can tell neither "set to zero" from "not set" nor a typo from either) or through `Math.max(1, Number(raw) || fallback)`: `POE_MAX_ITEMS_PER_ROOM`, `POE_MAX_REQUEUE_ON_RECONNECT`, `POE_RATE_LIMIT_BANNER_MIN_SEC`, `POE_ASK_CONFLICT_RATIO`, `POE_ASK_CONFLICT_ABS_GAP_C`, `POE_MIN_ASK_EVIDENCE`, `POE_MIN_CONFLICT_HEADLINE_C`, `PORT`, `POE_LANG_SKEW_WARN_RATIO` and `POE_STASH_TIMEOUT_MS` go through the same reader as everything else. `POE_STASH_PROBE` (a diagnostic tab index with no default) is the deliberate exception and is read by hand. A test with hand-written literals pins the defaults — see [bugs.md](bugs.md#b13--seven-more-settings-could-not-express-zero-fixed).

> **Per-deployment settings go in a (gitignored) `docker-compose.override.yml`** next to the compose file — `git pull` never touches it, so they survive updates. Put your user list (`POE_USERS`), display name (`POE_APP_NAME`), and any other per-instance env here:
> ```yaml
> services:
>   poe-price-tool:
>     environment:
>       - POE_USERS=youruser,teammate
>       - POE_APP_NAME=YourName
> ```
> **Applying changes:** env-only changes take effect on the next `docker compose up -d` (the container is recreated and re-reads its env) — **no `--build` needed**. A code update needs the full `git pull && docker compose up -d --build`.

> **⚠ A value set in the admin area beats this file.** Settings changed from the browser are stored in `/config/overrides.json` and folded into the environment **before** the server reads anything, so they win over `docker-compose.override.yml`. If a compose value appears to do nothing, check that first — the admin area's configuration section marks every such setting with *overrides your compose value*; see "Configuration from the admin area".

### Single-league coupling (multi-user pitfall)

`POE_LEAGUE` is a **single, server-wide** setting, but only the *starting* league: each user can switch their own league in the browser (per-room, see `set-league` in [PROTOCOL.md](../backend/v2/frontend/PROTOCOL.md)). Switching only changes what the **price check** queries. It does **not** move the Faustus store or the corpse store — both are pinned to whatever the background jobs were configured with, effectively `POE_LEAGUE` at deploy time.

**Net Worth pays for this silently.** A user whose browser league differs from the one the background jobs price gets a worse net-worth valuation without any error:

- Fungibles (currency, essences, scarabs, …) lose the Faustus source entirely and fall back to poe.ninja only (Faustus has no per-league selector on our side — it's whatever the store was built from).
- Itemised corpses go **completely unpriced** — the corpse store only holds prices for the league the background pricer targets.

This mostly matters right at league start, when someone forgets to flip their own browser league over from the previous one. There's no per-user override: if you run multiple leagues for different players, only one of them gets full Net-Worth coverage.

**POESESSID:** the **price check** works **anonymously** — no cookie needed (the shared RateLimiter queue suffices). The **Net Worth tracker** needs a per-user POESESSID, stored in `/config/networth-users.json`, never in the repo (see "Net-Worth-Tracker").

### `/config` volume

`./config:/config` is mounted for:

- **`networth-history.ndjson`** — the value-over-time series behind the History page: one appended line per user per minute, 15 days of retention. Its sidecar `networth-history-items.json` carries only the newest per-item breakdown, so a restart does not tear a hole into the series. A second sidecar, `networth-history-guard.json`, keeps the price brake's memory (running holds, prices it remembers for names that left the stash, the last C:D rate) so an update does not reopen the window in which a wrong price can enter the series. Entries expire exactly as they would have in memory, and a change of `POE_LEAGUE` starts it empty by itself.
- **`networth-sessions.json`** — farm and game sessions (`POE_NETWORTH_SESSIONS`): per user the running sessions and the ended ones still waiting for confirmation, each with a copy of the item breakdown it started from (about the size of `networth-history-items.json` per open session; a session that is still starting holds the copy taken at the start instead, when there is one), plus up to `POE_SESSIONS_KEEP` finished summaries without any breakdown. Versioned (`schema_version` 2); a file of schema 1, from before game sessions, is read as farm sessions and rewritten in the new form at the next save; a file this version cannot use is moved to `networth-sessions.json.broken-<timestamp>` with one warning, and one from a newer release is left alone while sessions run in memory. No account name, no POESESSID — the routing name and item names only. Deleting it forgets all sessions.
- **`reference-history.ndjson`** — the reference rail's own price series (`POE_REFERENCE_HISTORY`).
- **`rate-limit.json`** — the persisted ban gate (`POE_RATE_LIMIT_STATE`), so a restart resumes an active cooldown instead of probing GGG blindly.
- **`user-langs.json`** — which client language each user picked for himself (`POE_USER_LANG_STORE`). `{ "player1": "en", "player2": "de" }`. **Beats `POE_USER_LANGS`**; delete the file to fall back to the environment for everyone.
- **`overrides.json`** — the settings changed from the admin area (`POE_CONFIG_OVERRIDES`). **Beats the environment.** Two siblings belong to it: `overrides.applying` (present only while a start is in progress; it holds `failedStarts=N`, the number of starts in a row that never got as far as listening) and `overrides.rejected.json` (a set of overrides that broke repeated starts, parked so it can be inspected). Delete `overrides.json` to go back to compose/defaults entirely.
- **`update-request` / `update-heartbeat` / `update-result`** — the three files of the update button (`POE_UPDATE_DIR`). They only exist where `deploy/host-update.sh` is installed on the host, or where somebody has pressed the button at least once; a plain installation has none of them. See "Update button". Safe to delete: the request is a pending ask, the other two are a report. **Not here: the host script's lock and its staging files.** Those live in a directory of the script's own, next to this one (`…/config.host-update`), deliberately not in here — this directory is writable by the container, and the script runs as root over it.
- **`admin-password`** — one plaintext line, the password for the admin area of the settings page (`POE_ADMIN_PASSWORD_FILE`). Created with the default `admin` on first boot. **Change it before exposing the tool beyond the LAN** — see "The admin password".
- **`networth-store.json`** — the per-tab net-worth store (see "Net-Worth-Tracker"). It holds the CURRENT snapshot; the value-over-time series lives beside it in `networth-history.ndjson` (plus its `networth-history-items.json` and `networth-history-guard.json` sidecars). Back up `/config`, or accept that a volume loss erases both the snapshot and the history.
- **`faustus-store.json`** — the Faustus (GGG Currency Exchange) name→chaos map, refreshed hourly in the background. Persisted because GGG deletes old Faustus history: on boot the server loads this last-good map, so fungible valuation works immediately, without waiting for the first hourly refresh.
- **`corpse-store.json`** — itemised-corpse prices (name→chaos), sourced from the official Trade API by a budgeted background pricer (`POE_CORPSE_BUDGET_PER_HOUR` names/hour, stalest first) and cached ~6h (`POE_CORPSE_TTL_MS`). Prices **and** empty results (illiquid corpses) are cached, so a snapshot never re-fires a slow, rate-limited search. The valuation route only reads this store — it never queries the Trade API inline. `Imperfect …` corpses are valued 0 without any query. An expired POESESSID trips a **circuit-breaker** (all corpse trade calls short-circuit until the cookie is renewed) rather than hammering GGG with 401s.
- **`data-refresh/`** — adopted data-source snapshots + update state of the background data auto-update (see "Data auto-update"): versioned copies of the APT item/stat data (`apt/v-…/`), plus `base-names.json` and `state.json` (the stored `ETag`/`Last-Modified` validators), `lang-work/` (the export cache of the language generator, ~32 MiB, see below), a `package.json` (`{"type":"module"}`, so `client_strings.js` can be imported from below this directory) and short-lived `.client-strings-*.js` files the check imports and deletes again. Safe to delete as a whole — the server falls back to the image's baked-in data and re-fetches on the next check.
- **`release-check.json`** — the release check's memory (`POE_RELEASE_CHECK_STATE`): when GitHub was last asked, when it may be asked again, what it answered (the latest release's version, tag, link and date), and the `ETag` for the next conditional request. Safe to delete: the check starts empty and asks again about 10 minutes after the next start. A file that cannot be read is logged once and treated as empty (`[release-check] state file … is not usable` when the content is not a JSON object, `… could not be read` when the file cannot be opened); it never stops the server from starting.
- **`networth-users.json`** — the per-user credentials (`accountName` + POESESSID; path `POE_NETWORTH_CONFIG`). Only Net Worth needs it: the stash reads use the session cookie, the price check does not. It holds secrets: see "Net-Worth-Tracker".

Which of these files a backup needs, and what is lost with each: [runbooks.md → Backup and restore](runbooks.md#backup-and-restore).

**A file a store cannot use is moved aside, never overwritten.** `networth-store.json`, `faustus-store.json`, `corpse-store.json`, `networth-sessions.json` and `networth-history-guard.json` carry a `schema_version`, `networth-history-items.json` a format number `v`; `user-langs.json` and `data-refresh/state.json` are checked for their shape. When one of them is not valid JSON, has the wrong shape, or carries an older version this release cannot migrate, the server renames it to `<name>.broken-<timestamp>` (for example `networth-store.json.broken-2026-11-02T10-15-00-000Z`; a second one in the same millisecond gets `-2`), logs one warning with the path and the reason, and starts that store empty:

```
[networth-store] /config/networth-store.json is not usable (invalid JSON at position 812) — moved to /config/networth-store.json.broken-2026-11-02T10-15-00-000Z; starting empty, the stash is read again tab by tab
```

The warning never quotes the file's content. Nothing reads a `.broken-…` file again: look at it if you want to know what happened, then delete it. The net-worth one holds item names, prices and account names; none of them holds a POESESSID. Where a warning ends differently: the brake's memory with "starting with an empty memory: the price guard judges from the next recorded point as after a first start", the items sidecar with "starting without a breakdown: the next point has no item movers and skips the price guard", `data-refresh/state.json` with "starting with an empty state: the image's baked-in data stays live until the next check fetches the sources again".

**Without `data-refresh/state.json` the server offers what the image carries.** The pointer to the adopted snapshot goes with that file, and the baked-in data normally holds no German set (the generated `data/de` files are not in the repository), so the server offers English only: a player set to German in `POE_USER_LANGS` or `POE_LANG_DEFAULT` gets `503` (`no parser for language "de"`) on every item, and a German choice stored on the settings page is parked (out of force, kept in `user-langs.json`, see "Client language at runtime"). After a broken `state.json` the German set comes back when the first apt check after the start (120 s by default) has generated it again. After a `state.json` that could not be moved or not be read at all (below), the data auto-update stays off, so the German set and the parked choice come back only once the file is fixed or removed and the server restarted.

**A file that cannot be moved (read-only volume) or cannot be READ at all (wrong owner or mode) is never written over either.** A store whose file cannot be moved runs in memory only and leaves it untouched until you fix or remove it; for `data-refresh/state.json` the data auto-update stays off instead (the image's baked-in data stays live). A file that cannot be read:

- `user-langs.json` runs in memory only and logs `[user-langs] could not read … — starting from POE_USER_LANGS only and not writing over it; fix or remove it and restart`.
- The four stores with a `schema_version` (net worth, Faustus, corpses and the farm sessions in `networth-sessions.json`) stop the server from starting, with the read error in the log.
- The brake's memory (`networth-history-guard.json`) logs `[networth-guard] … could not be read (…) — starting with an empty memory and not writing over it; fix or remove it and restart` and runs in memory only.
- The items sidecar logs `[networth-history-items] could not read … (…) — starting without a breakdown: the next point has no item movers and skips the price guard, and not writing over it; fix or remove it and restart` and runs in memory only.
- `data-refresh/state.json` logs `[data-refresh] could not read … (…) — data auto-update off and not writing over it, using the baked-in data; fix or remove it and restart`.

A file from a **newer** release (its `schema_version`, or `v` for the items sidecar, is higher than this one knows — typically after rolling back to an older image) is left exactly as it is. The store runs in memory only and logs `… has schema_version N, newer than the M this version reads (written by a newer release?) …` (the sidecar says `has format N`), and the admin area's runtime list shows it as `net-worth store writable` / `farm sessions writable` / `Faustus store writable` / `corpse store writable` / `net-worth guard memory writable` with the value `0`; the items sidecar has no row there, only the warning. The brake's memory from a newer release is left alone the same way and stays in the process. Updating again picks the file up as if nothing had happened; to stay on the older release, move the file away and restart (the store then starts empty and writes a new one).

**While the items sidecar is left untouched** (newer, unreadable, or broken and not movable), the brake's memory `networth-history-guard.json` keeps the remembered prices of every name itself, including those it otherwise leaves to the sidecar, so the brake still holds across a restart. It does the same after every sidecar write that failed (a full disk, for example). Such a write is logged once per error code: `[networth-history-items] could not write … (ENOSPC) — the file keeps its previous content; until a write succeeds, a restart finds no breakdown for a newer point (the next point then has no item movers and skips the price guard), and the brake's memory keeps every price itself`. After a recorded point, the sidecar on disk then still holds the point before, and a restart does not use it. When the write at a change in the set of stash tabs failed, the sidecar on disk still holds the breakdown that change dropped, anchored on that user's newest point; the brake's memory, written right after, marks that entry as stale (`stale` in `networth-history-guard.json`), and the next start leaves it out with the line `[networth-history-items] not adopting the breakdown of "<user>" … a change of stash tabs dropped it before the restart and the write that should have removed it failed` ([B35](bugs.md#b35--a-breakdown-dropped-at-a-change-of-stash-tabs-came-back-after-a-restart-when-the-sidecar-write-failed-fixed)). The mark needs that write of the brake's memory to land: when it fails as well, or the memory file is left untouched (newer release, unreadable), the next start adopts the dropped breakdown again.

**How the container handles /config permissions.** PID 1 starts as **root** on purpose (`docker-entrypoint.sh`) and drops to the service user itself; there is no `USER` directive in the Dockerfile. Docker creates a missing bind-mount target as `root:root` (755) while the service runs as UID 1000, so without this every write failed with `EACCES` and nothing persisted, silently. The entrypoint decides by OWNERSHIP, after checking whether the service user can actually create a file there:

- **Owned by root** — the folder docker created because the bind-mount target did not exist. Nobody else has a claim on it, so the entrypoint takes it (`chown -R`).
- **Owned by anyone else** — a NAS share (Unraid uses `nobody:users`) or a deliberate choice by the operator. Ownership is left alone: the entrypoint tries to join the folder's group instead, and if that does not work it says so in the log rather than rewriting the share behind your back (taking over a share can break SMB access to the same folder, and the operator cannot easily undo it).

Ownership decides, not the permission bits: on a share that is group-writable for a group the service is not in (exactly the Unraid case) `test -w` reports "not writable", and chowning on that basis would rewrite the share's ownership recursively, including every existing file. Afterwards it `exec`s the server under UID 1000 via `setpriv`, so the server itself never runs as root. Pinning `user:` in compose still wins: the script then runs unprivileged and simply execs the command. The log line `/config is owned by uid N and not writable` and its one-time fix: [runbooks.md → /config is not writable](runbooks.md#config-is-not-writable).

### Data auto-update (background)

The three vendored data sources go stale with every league patch, and the failure is silent (an unknown unique parses as `item.unknown`, an unmapped metadata id drops out of the net-worth valuation). The server therefore keeps them fresh **itself** (`backend/v2/data-refresher.mjs`) — no manual step, no redeploy:

| Source | Feeds | Upstream |
|---|---|---|
| APT item/stat data (`renderer/public/data/en/*`) | price-check parser, mod matcher, net-worth item classification | Awakened PoE Trade `master` |
| `base-names.json` | Faustus metadata-id→name bridge | `repoe-fork.github.io/base_items.json` |
| localized data set (`data/de/*`) | the second parser — a user on a German client | **none. Generated locally** from the English set above plus GGG's game data (`patch.poecdn.com`). Only exists when `POE_USER_LANGS`/`POE_LANG_DEFAULT` or a stored per-user choice (`/config/user-langs.json`) name a language beyond `en` |

How it behaves:

- **~Daily checks** (`POE_DATA_REFRESH_MS`), plus one look **shortly after every boot** (the APT data after 2 min, the base names after 7 min, so a restart right after a league patch picks the new data up within minutes and the two never fire at the same moment). The localized set has no timer of its own: it is checked as a follow-up step of every APT check, and only when a language beyond `en` is in use.
- **Conditional requests**: stored `ETag`/`Last-Modified` validators are sent along; on a day without upstream changes not a single payload byte flows.
- **Validate before adopt**: a download is parsed and schema-checked (the same join fields the net-worth bridge relies on, plausible line counts, importable `client_strings.js`, a non-collapsed seed) and its search indices are regenerated **before** anything is swapped in. A broken or truncated download is rejected with a warning and the old data stays — a dead upstream can never take the tool down.
- **Effective at runtime**: an adopted APT snapshot is hot-loaded into the engine (versioned dirs under `data-refresh/apt/`, engine reload with automatic rollback if the reload fails); a new base-names map reaches the Faustus pricer with its next hourly tick. No restart, no self-restart.
- **Persistent**: adopted snapshots live under `POE_DATA_REFRESH_DIR` in the `/config` volume and are preferred at the next boot, so updates survive redeploys. If the dir isn't writable (local run without the volume), the feature silently disables, like the other `/config` stores.
- **Bilingual snapshots**: a snapshot dir holds `data/en` and, once a localized set exists, `data/de` **next to it** — never instead of it (the localized load path still reads `data/en/client_strings.js`, and both engine instances share one process-wide data root). The localized set has no upstream, so **every adoption carries the existing one forward unchanged**, exactly like `item-drop.json`/`patrons.json`; English may run ahead while the localized set stays on its last good state. The boot check demands `data/de` exactly when the snapshot was adopted with one, so an English-only install is unaffected and a half-written localized tree is still rejected. If a snapshot ever lost a set that a live parser needs, the reload vetoes the adoption and both languages stay on the previous snapshot.
- **The localized set regenerates itself** — as a **post step of the `apt` check**, not on a timer of its own (the generator reads the active snapshot, and a concurrent `apt` check is free to prune it away underneath; riding along inherits that check's overlap guard). What triggers a run is **a comparison, not an event**: every set carries a `build-info.json` saying which **patch version**, which **English skeleton** and which **generator version** it was built from, and every tick compares all three with what it would build from now. Equal → nothing happens. Different → generate. The generator version is a hash the server computes at runtime over the generator's own files (`lang-data-gen.mjs`, `lang-derive.mjs`, `lang-statdesc.mjs`, `lang-pseudo-matchers.json`) and the installed versions of `pathofexile-dat` and `pathofexile-dat-schema`, so a repaired derivation reaches an installation without waiting for the next game patch: an update that touches any of those files rebuilds the localized set once, on the next `apt` check. A set built before the version was recorded is rebuilt once as well; if a file is missing the version counts as unknown, which also rebuilds once and then holds. It is a level and not an edge: after a failed run the difference simply stands, so every tick either retries or reports `failed`, and the source ages into the stale note below like any other (an event-driven trigger would report "patch unchanged, nothing to do" the next day and stay healthy forever). A successful run writes a **complete new snapshot** (English tree byte for byte, aux files, the new localized tree) and swaps it in through the same validated reload-with-rollback path as an upstream adoption. The game-data export works in `POE_DATA_REFRESH_DIR/lang-work` and caches ~32 MiB of GGG bundles under it (the exporter clears that cache itself on a patch change) — worth knowing when sizing the `/config` volume, and the reason it lives there rather than in a container-local tmp dir that every restart would throw away.
- **Skew policy**: English comes from upstream and is adopted **immediately**, even when the localized set cannot follow — English users do not lose currency over a language they do not use. The localized set catches up on the next generation run; until then the old tree stays live (carried forward) and its own row says so. Whether the localized set has fallen behind in CONTENT is a different mechanism — the settings page's skew view, `lang-skew.mjs`.
- **What makes a generated set unusable, and what only makes it INCOMPLETE** — two findings with two answers (`docs/bugs.md` B23). A run is thrown away — nothing written, previous set stays live — when it would **lose** coverage the live set already has: stats that carry a German matcher today and would not afterwards. That is a broken derivation, and the bar is `POE_LANG_MAX_COVERAGE_LOSS_RATIO` (1 % of what the live set covers). A run is **kept** when the only stats without a German matcher are ones the previous set had no matcher for either — English lines whose text the derivation has no source for, because upstream has run ahead of the patch or ships a kind of matcher the derivation does not know yet. Refusing such a run closes none of those gaps (the set that would stay live does not carry those stats **at all**, and an empty matcher list and a missing stat are the same thing to every reader), so the incomplete-but-newer set wins, and the log says how incomplete:

  ```
  [data-refresh] data/de (the English snapshot moved on; 8773 of 9278 stats carry a
  matcher, 505 do not) generated from patch 3.29.3.1.2 (…) into v-…
  ```

  The container log lists every affected ref in full, under two headings — `COVERAGE LOST against <dir>` (what this run gave up, the actionable half) and `COVERAGE GAP (new, the previous set did not carry these either)`. The unresolved matcher strings are listed too, split into "on stats the previous set already had" (a defect here) and "on stats that are new since the previous set" (no source for them yet); that split identified the second half of B23, where the new matchers were plain skill and gem names whose German tables were exported on every run and never read. In the browser the same distance is the skew view's `matchers` row (`lang-skew.mjs`), which warns above `POE_LANG_SKEW_WARN_RATIO` — where a gap that never closes becomes visible, because the generator keeps succeeding.
- **Where the patch version comes from.** The generator needs it to build the CDN path (`patch.poecdn.com/<patch>/Bundles2/…`), and nothing local provides it. No GGG endpoint may be asked: the CDN answers 404/403 to every guess at a listing, and `pathofexile.com` is off limits here (ban history). It is looked up at **`https://ggpk.exposed/version?poe=1`**, which answers with one line — the CDN base of the current patch; the `repoe-fork` export pipeline resolves its own version with the same endpoint, and that pipeline's `base_items.json` is already a daily dependency of this tool. The answer is validated, not believed: the host has to be `patch.poecdn.com` and the version digits and dots — **however many parts** it carries. Four is the usual shape, five happens (a hotfix on a hotfix); a pattern that expected at most four once froze the German set for four days (`docs/bugs.md`, B22). Refused is everything without the shape of a version — a letter, an empty path, a path segment like `../../etc` — because the string is pasted straight into a CDN path. **`POE_PATCH_VERSION` overrides the lookup outright** — set it when the service is gone or answers wrong, in the compose file or **in the admin area** (Settings → admin area → server settings). It takes effect at the next check without a restart, and the field validates it with the same pattern the start does. Without either, the check reports `failed` (never a guessed version): an installation that cannot determine the patch can no longer keep its localized set current, and says so. What each failure of the lookup looks like and how to read it: [runbooks.md → The patch lookup failed](runbooks.md#the-patch-lookup-failed).
- **Pinning the patch version, and what watches the pin.** The pin has two failure modes, both easy to miss:
  - **Valid, but not a real patch.** `3.29.9.9` passes the pattern. The CDN then refuses every file the export asks for, and a retry cannot fix a value somebody typed in, so the class is `rejected` rather than `unreachable` ("the next check tries again"), and the reason names the pin: *"the game-data export asked the patch CDN for … and was refused. The patch version 3.29.9.9 it asked for comes from POE_PATCH_VERSION, not from the lookup — every check repeats the same request until that pin is changed or cleared."* `pathofexile-dat` prints that line on exactly one branch, `!response.ok`, so an answer did arrive; the line does **not** carry the status code, so a 404 and a 503 look alike — which is where the pin decides: with a pin every retry asks for the same version, without one the version came from the lookup.
  - **Valid and right, until the next patch.** Then every check succeeds, reports `unchanged`, and the localized set is frozen on last league's data with no age warning anywhere, because a source that is checked daily never goes stale. So **the lookup is asked even when the pin wins**, and a disagreement is reported as a warning on a check that otherwise succeeded:

    ```
    Note on lang-data: POE_PATCH_VERSION pins the patch to 3.29.2.1;
    https://ggpk.exposed/version?poe=1 reports 3.30.0.1. The localized set is
    built from 3.29.2.1 until the pin is changed or cleared.
    ```

    The pin still wins — nothing here overrules a human, and "the pin is stale" and "the lookup is wrong again" produce the identical difference, so the message says what was seen, not what it means. A lookup that is **down** while a pin stands costs nothing and says nothing: that is the situation the pin was set for.
- **"Check now".** **Settings → admin area → server settings → "Check now"** runs every check immediately and redraws the status line with the result, so a pin that was just cleared, corrected or set can be verified without waiting a day. It sits behind the admin password like the restart button, because it starts outbound traffic on demand. It refuses while a check is already running (HTTP 409) and for `POE_DATA_CHECK_NOW_COOLDOWN_MS` after one finished (HTTP 429, with the remaining wait in the answer), because one press is a lookup, five conditional fetches (the four APT files and `base_items.json`) and possibly a multi-megabyte CDN download. `POE_DATA_REFRESH_DISABLED=1` turns it off along with everything else it would trigger.
- **The game-data export** is a child process (`pathofexile-dat`). Its exit code and stderr are read, so the ways it can die are told apart instead of arriving as the message for a *misspelled language name* (`docs/bugs.md` B24); the messages and what to do about each: [runbooks.md → The game-data export failed](runbooks.md#the-game-data-export-failed).
- **A language configured without data** (`POE_USER_LANGS` names `de`, but no `data/de` exists yet — a *stored* choice for such a language is parked at startup instead, out of force and kept in the file, see "Client language at runtime"): English keeps working, and that user's `POST /item` is answered with **503** plus one warning line at startup. It is deliberately not parsed as English — a wrong-language parse comes back as a plausible item, not as an error. The first generation run after that fixes it without a redeploy. The first time a language is switched on the startup log looks like a crash and is not: [runbooks.md → A language was just switched on](runbooks.md#a-language-was-just-switched-on).
- **One line per check** — silence means "not running", never "nothing to do". Three sources checked once a day = three lines a day (`lang-data` only on an install that serves a second language):

  ```
  [data-refresh] apt check updated — APT data updated (v-2026-07-31T04-02-11-903Z): items.ndjson 41988->42130 lines (+150/-8); upstream Tue, 29 Jul 2026 22:14:07 GMT -> Thu, 31 Jul 2026 03:41:52 GMT
  [data-refresh] lang-data check unchanged — data/de built from patch 3.29.2.1 and the current English snapshot; data from 2026-07-31T04:03:44.118Z
  [data-refresh] base-names check unchanged — upstream reported no change (304); data from 2026-07-24T04:07:19.310Z
  ```

  The detailed `REJECTED` / `could not be applied` warnings appear above the outcome line — they carry the reason, the outcome line carries the outcome.
- **Visible when a source goes quiet**: every check persists its timestamp in `data-refresh/state.json`; the server hands the last **successful** check per source to the browser (`data-status`, see `frontend/PROTOCOL.md`). A source whose last success is older than `POE_DATA_REFRESH_MS × POE_DATA_STALE_TICKS` (default 3 ticks = 3 days) shows up in the status line every page reserves under its heading — informational, the tool keeps running with the data it has. The ageing happens in the browser, so a schedule that died without ever sending another message still surfaces.
- **…and it says WHY, and whether that is yours to fix.** The reason of the last failed check is persisted with it and travels into that note, together with the CLASS of the failure:

  | Class | The note adds | Meaning |
  |---|---|---|
  | `unreachable` | "The other side did not answer — nothing to do here, the next check tries again on its own." | An upstream or the patch lookup was away; or the patch CDN refused a file for a patch version that came from the lookup |
  | `rejected` | "An answer arrived and this tool refused it. That does not fix itself…" | A snapshot that failed validation, a lookup answering something that is not a version — **or the patch CDN refusing a file for a version that `POE_PATCH_VERSION` pinned**, because every retry then asks for the same one |
  | `incompatible` | "The data format has moved past this build — update the container…" | The game-data export cannot read the current format with this image. Shown **immediately**, without waiting for the source to go stale: that diagnosis is certain the moment it is made |
  | `unknown` | **nothing** | Nobody classified this failure. The reason is shown as it is and no remedy is claimed |

  **The reason is a finding; the advice belongs to the class.** Reasons state what was seen and nothing else (two authorities for one question would disagree when the class changes). Where a class-level sentence is not enough, the detail is here: a repeated `incompatible` on a missing COLUMN after a container update means `TABLE_COLUMNS` in `lang-data-gen.mjs` is what has to move.

  **A check can also carry a warning**, which is not an outcome: a check can succeed and still have something to report — built for a pinned patch version (see "Pinning the patch version" above). A warning is shown whatever the outcome and whether or not anything is stale, and it carries **no** advice.

  The class is set where the failure happens and is never derived from the wording of the message afterwards, which is why `unknown` exists at all. The reason is foreign text — it is filtered and cut to `POE_DATA_STATUS_REASON_MAX` characters before it is stored, **and filtered again when it is read back out of `state.json`**, because that file outlives the build that wrote it. The filter works at VALUE granularity: the VALUE a credential-shaped name is handed is masked (`token=***`, `Authorization: Bearer ***`, `POESESSID ***`) and the words around it stay. The update block's host-output filter drops a whole LINE that names anything credential-shaped instead, which is right for a multi-line build log and wrong for a one-line reason (`key count` or `Unexpected token` would come out as nothing but the placeholder). Both catch names and shapes only: a bare secret on a line that names nothing passes both alike.

The manual CLIs (`npm run update-apt-data`, `node backend/v2/base-names-gen.mjs`) refresh the **checked-in** copies in the repo (so a fresh image also starts reasonably current) and serve as an emergency hatch; a running deployment does not need them. `npm run gen-lang-data -- --lang de` is a different kind of tool: it generates the localized set **locally** and does not refresh a checked-in copy — the generated `items.ndjson`, `stats.ndjson` and `text-pairs.ndjson` are not part of the repository (`renderer/public/data/.gitignore`). It looks the patch version up like the background run does; `--patch 3.29.2.1` and `--dry-run` are there when you want to pin or just look.

### Settings page & admin area (`/settings.html`)

One page for everything that gets configured, plus the place where the tool reports what it could not do. Sections from top to bottom:

**Client language** comes first, above the credentials: it is the only user-facing setting whose wrong value fails silently (the item is not parsed at all — no card, and no error in the game either), so it sits where it is read without scrolling and carries the explanation of what it actually selects. It is a switch, not a form: choosing a language saves it. Storage and precedence: "Client language at runtime".

**Sync settings** are the net-worth credentials — account name and POESESSID for the user the `ppt_user` cookie names. The Net Worth page has no credentials dialog of its own: its "Sync settings" button and its sync status line link to this page. The stored POESESSID is never delivered to the browser in any form, an empty field keeps it, and a save takes effect on the next background sync tick.

**Releases** is visible without the password: the installed version of this server (or "unknown" when it cannot read its own), the latest release GitHub reported (version, date, link to its page; or "No release published yet" / "Not checked yet"), when the last check ran and what it found, and one sentence on a failed check (GitHub not reachable, the request refused — usually its rate limit —, or an answer that could not be read, e.g. a tag that is not a version number). It ends with the reminder that the server is updated by whoever runs it and that every player's hotkey daemon is its own clone. The same facts reach every page as one line in the status line when a newer release exists. See "Release check".

**Sources** is visible without the password: one row each for Faustus prices (GGG Currency Exchange), poe.ninja Chaos:Divine, poe.ninja prices (every other poe.ninja overview: uniques, gems, beasts, the net-worth exchange map) and the Trade API, with the time of the last success and a state:

- *stale for …* — the last success is older than the source's threshold (`POE_SOURCE_STALE_MS`, raised for Faustus and poe.ninja Chaos:Divine to twice their own refresh interval). The two sources on a timer (Faustus, poe.ninja Chaos:Divine) go stale by age alone, because their timer should have refreshed them; poe.ninja prices is asked on demand and goes stale only when its last attempt failed, so an old success with no failure since stays *current*; the Trade API has no threshold and is never stale (its outage is the ban).
- *current* — a last success is known and the row is not stale.
- *no answer yet* — no success known, an attempt failed, and the row is not stale (yet).
- *not asked yet* — neither a success nor a failure since the server started, which is normal for the Trade API until somebody runs a price check. The two poe.ninja rows are asked by the warm-up at boot (the C:D ratio, and the reference rail's beasts for poe.ninja prices), so for them it shows only in the first moments after a start, or with `POE_REFERENCE_DISABLED=1` until the first periodic refresh (`POE_CD_REFRESH_MS`).
- *switched off*; *paused until …* — the trade API during a GGG ban.

A source whose last attempt failed also shows that failure's time and reason. The status line on every page shows the same derivation: "Price sources are behind: …" names each stale price source with its age and reason, and "The tool is partly blind: …" appears when at least one price source is stale and none has a success younger than its threshold (naming the time since the most recent success), or when at least two parts are out at once (prices, a trade ban, an expired POESESSID). The poe.ninja times are kept in memory, so after a restart they count from the start; the Faustus time comes from its store and survives. The Chaos:Divine tile ages the same way: `live · poe.ninja` turns into `stale · poe.ninja · 5 h` (amber) once poe.ninja's last answer is older than the threshold.

**Admin area** (bottom) is behind a password. It holds the blocks below; the last three (offset, provenance, display texts) are one block on the page, because they answer three halves of one question: how far apart the language data sets are, where the localized one came from, and whether the texts around it followed.

- **Server settings** — the allow-listed configuration this installation can change while it runs, in three blocks: what takes effect immediately, what needs a restart, and — set apart with its own explanation — the settings that decide how often the tool asks GGG, poe.ninja and the data sources. Plus the **Restart** button. See "Configuration from the admin area". If repeated starts with those settings failed, an alarm sits above everything else in the area saying they were quarantined and are not in effect; saving anything clears it, since the file it describes has then been replaced. Under the alarm, and only while it applies, sits the notice that the admin password is still the default.
- **Update to a newer version** — a block of its own, not a second button beside the restart: a restart is harmless and frequent, an update replaces the running code. It shows which commit this container was built from, asks a script on the host to `git pull` and rebuild, and reports how that went. Disabled with an explanation where that script is not installed — which is every installation until somebody installs it. See "Update button".
- **Check for a newer release** — next to the update block: the **Check for updates** button asks GitHub now (`POST /admin/release-check`) and prints one sentence — up to date, `<version>` is available, no release published yet, or the failure. It only reports; it installs nothing and it works whether or not the daily automatic check is switched on. One check at a time, and 60 seconds between two manual checks.
- **Everything else this server runs with** — a read-only list at the end of the area, so the effective configuration can be read without a shell on the server. Filtered by name; nothing that could be a credential is in it.
- **Gaps the tool found by itself** — collected while price-checking, grouped by language, sorted by frequency:
  - *Failed parses:* the engine refused a clipboard text, so no card reached the browser. The row carries the item-class header as its signature, the engine's reason, and the full triggering text behind a disclosure so the failure can be reproduced. Two items of the same class failing for the same reason are ONE counted row — the rolls are not part of the identity.
  - *Unresolved mod lines:* the item parsed, but a line matched neither the vendored data set nor GGG's stat catalogue. The card shows it read-only and the search ignores it, so the returned price is the price of a different item — the more dangerous of the two, because nothing looks broken.
  - **Lifetime and size:** in memory only. The list starts empty after a restart (a gap that matters recurs the next time that item is checked), and it is capped at `POE_GAP_LOG_MAX` entries per kind. Over the cap the *least frequent* entry is dropped and the view prints how many were dropped, so a truncated list never pretends to be complete.
- **Dataset offset between the languages** — how much of the English set a localized one failed to carry: item names, stat entries, stats without any matcher, and stats whose extended (`Ctrl+Alt+C`) mod description is missing. Each row is measured against the English set the container is *actually* serving, and turns into a warning above `POE_LANG_SKEW_WARN_RATIO`. Two states need no threshold: a configured language with no data set at all, and refs that exist only in the localized set (zero by construction — anything else means the generator left its own design). This compares two sources; the `data-status` staleness note only reports each source against itself.
- **Where the localized set comes from** — under the offset rows, because the offset is a *distance* and says nothing about whether anything is still producing the set. Read out of `build-info.json` next to the data the container is serving: when it was generated, from which game patch, how many stats carry a matcher, how many the run **lost** against the set it replaced (where a regression shows up), how many are newly without one, and the item side — translated, kept English. A set generated before this bookkeeping existed says so; its numbers are shown as absent, never as zeroes. A line in warning colour appears when the run met an **item namespace with no name source at all**: every entry of it keeps its English name and nothing else on this page moves (the offset rows match, the coverage numbers are about stats) — the quietest gap the data set has.
- **Display texts (`client_strings.js`)** — the English file is refreshed from upstream every day, the localized one is hand written and ships **with the image**. A key upstream adds is absent for the other language, and if the parser reads it, the failure lands on a user of that language as an unexplained parse error. The key sets are compared at every English adoption and the difference is named here and in the log. The tool knows which keys differ, not which the parser reads, so it says "any of them the parser reads is missing", never that something will fail. **A container update closes this; a data refresh cannot.**

**What this is not:** the tool sends nothing on its own — no mail, no push. You do not have to *search*, you do have to *look*.

#### The admin password

Plaintext, one line, in `POE_ADMIN_PASSWORD_FILE` (default `/config/admin-password`). The file is created with the default value `admin` on first boot if it is not there. It is read on **every** request, so changing it takes effect on the next click — no restart, no cache to clear (setting it: [runbooks.md → Set the admin password](runbooks.md#set-the-admin-password)).

> **Change it before this tool is reachable from anywhere but your home network.** The default is `admin`, and it is printed in this repository for everyone to read — on an exposed instance it is not a weak password, it is a published one. Everything else in `/config` is plaintext as well: `networth-users.json` holds POESESSID session cookies, and those are full account control if they leak.

It guards the read-only diagnostic views, the **Restart** button (it ends the process) and the **server settings** (it writes the configuration file the next start reads). The trust model stays LAN, no authentication, one plaintext password; because the default being in force matters, the tool says so in two places while it is:

- a block of `[admin]` lines in the container log at **every** start,
- a notice in the admin area itself, above the settings it guards.

Both disappear on the next request after the file is changed. Nothing is forced: a tool that demanded a new password before it would run could lock you out of your own box on a LAN it was never exposed on.

The mechanism is a **partition, not a security boundary**. This backend has no authentication at all (identity is a freely settable cookie, the LAN is the trust boundary), and the admin area does not add one: it keeps the ordinary user out of a view that is none of their business and lets whoever runs the box in without ceremony. State model: the browser keeps the password in `sessionStorage` and sends it as the `X-Admin-Password` header on every admin request. There is **no session on the server**, no token and no expiry — closing the tab is the logout, and rewriting the password file locks every open tab out at its next request.

### Client language at runtime

The language a user's game client runs in decides which parser his pasted items go through. The player sets it himself on the settings page, without shell access or a restart; `POE_USER_LANGS` is only the starting value. It sits above his own POESESSID and deliberately **not** behind the admin password. It is a plain selector with no save button — selecting a language is the save — and the paragraph over it says what the setting is, because the failure mode is silent: a user who picks the language of the *website* rather than of his *game* gets no card and no error when he copies an item. When only one parser is live the selector is shown disabled with that reason next to it rather than hidden, and when the server cannot save the choice (`/config` not writable, or a `user-langs.json` it could not read or could not move aside) the page says out loud that the choice will not survive a restart and that the server log says why.

**The file beats the environment.** The choice is stored in `/config/user-langs.json` (`POE_USER_LANG_STORE`); `POE_USER_LANGS` is only the value a user starts on until he has chosen once — if the environment won, the next deploy would silently revert somebody's own choice.

```json
{ "player1": "en", "player2": "de" }
```

- A **stored language the tool does not support is dropped, never fatal**: one warning names the user, the value and the reason, that user falls back to his `POE_USER_LANGS`/`POE_LANG_DEFAULT` value, and the next saved choice of any user writes the file without the entry. (`POE_USER_LANGS` itself stays a hard startup error — it is written by hand, this file is not.)
- A **stored entry of a user who is not in `POE_USERS` is kept, not dropped**. It is out of force, and the log says `[user-langs] keeping stored language "de" for "<user>" out of force: not in POE_USERS (…) — the choice stays in /config/user-langs.json and applies again at a start with "<user>" back in POE_USERS`. Saving another user's choice writes it back, so a user put back into `POE_USERS` later is on the language he picked himself. It never comes back without a restart, since `POE_USERS` only changes with one.
- A **stored language without a loaded parser is parked, not dropped** (its data set is missing from the active snapshot, or its parser failed to load). The user is on his `POE_USER_LANGS`/`POE_LANG_DEFAULT` value for now, and the log says `[user-langs] parking stored language "de" for "<user>": no parser is loaded for it — using the configured value for now; the choice stays in /config/user-langs.json and applies again once a "de" parser is live …`. The entry stays in the file: saving another user's choice writes it back. It is in force again at the next start with that parser live, or without a restart when a data update brings the missing data set (the log then says `a "de" parser is live now — "<user>" is back on his stored choice`, and his open tabs switch). A parked user who picks a language himself replaces the parked entry.
- **Broken JSON does not stop the start.** The file is moved to `user-langs.json.broken-<timestamp>` and the server comes up without it, loudly (see "A file a store cannot use is moved aside" under the `/config` volume). A file that cannot be moved, or cannot be read at all, is left as it is and the choices of this run are kept in memory only.
- The switch is immediate: the value is persisted first, then applied, then pushed to every open tab of that user over the WebSocket. No restart.

**Which languages can be chosen** is what the server has a *live parser* for, not the list it supports in principle. At boot it loads one parser per language whose data set is in the active snapshot, so a language somebody once configured stays selectable even after the last user has left it. A language that has **never** been configured has no data set and therefore cannot be picked — set `POE_LANG_DEFAULT` (compose, or the admin area's configuration section) to it once and restart; the data auto-update generates the set, and from then on every user can switch to it in the browser.

**Everything selectable is kept up to date.** The data auto-update refreshes the same set of languages the switch offers — configured *plus* chosen by a user *plus* present in the active snapshot — so no pickable language's data set ages quietly. The set is fixed once per boot, which is enough: a language only becomes selectable by having a parser, every parser belongs to a language of that set, and `POE_LANG_DEFAULT` is a *restart* setting, so every way to make a language *outside* the set selectable goes through a start. A language *in* the set whose parser was down at boot (its data set was missing) becomes selectable without one: the engine reload after the next successful data update retries every parser that is down.

### Configuration from the admin area

The configuration section of the admin area writes `/config/overrides.json` and folds it into the process environment at the next start — or immediately, for the settings that are read at use time.

**The override wins over the real environment.** `docker-compose.override.yml` is what the box was started with; the override file is what a human deliberately submitted through the running tool, and a button that silently did nothing whenever compose set the same key would be the failure this exists to remove. The price is that a compose value can sit there doing nothing, so the view names the **source** of every setting (`override` / `env` / `default`) and marks the ones that are shadowing an environment value. When something does not behave like compose says it should, look here first.

The section is grouped by that answer — *takes effect immediately* above, *needs a restart* below — and a value that has been written but is not in force yet is marked on its own row and once more above the table. A row shows where its value comes from in words rather than as the raw `source` token, and an entry that is in the file but fails validation is labelled as such instead of being drawn as if it were the value in force.

**Below both sits a third block: *How often this tool asks other people's servers*.** The settings in it decide how much traffic the background jobs send to the trade API, to poe.ninja, to GGG's exchange feed and to the data sources; they are kept apart from the display name and the league picker on purpose. The block carries one paragraph saying why, and every row says which direction adds requests (a budget grows with the number, an interval or a cache lifetime with the *smaller* one). Only request COUNT gets in: `POE_MAX_LISTINGS` looks like a traffic setting and is not, because all ten listings arrive in one call, and `POE_NETWORTH_LIST_TTL_MS` is not one either (see its row). Which rows belong there is served by the endpoint like everything else, so the page cannot hold a stale opinion about it.

> The **ranges** behind those fields are the ones the environment accepts (`numeric-settings.mjs`), not tighter ones invented for the browser. They are tight because a ban was reported to apply to the whole address: the floors are 30 s between refresher ticks, 10 min for the post-429 cooldown, 2 min between corpse queries, 1 h for the corpse cache, the Faustus pass and the data check, and 15 min for the C:D refresh (poe.ninja's limit); the corpse budget stops at 30 an hour, which is all its pacing can deliver anyway. Every field can still be moved in the direction that sends *less*. Treat the defaults as the tested configuration and change them by factors, not by orders of magnitude.

Per setting the view shows whether a change is `live` or needs a `restart`. Nothing is guessed: a value the server reads once into a constant at startup is declared `restart`. **Restart** is a button of its own — it answers, then ends the process cleanly. There is deliberately **no docker socket** mounted for this: handing a container that has no authentication control over its own host daemon is a far bigger hole than a restart button is worth.

**Whether the tool comes back is a property of your deployment, not of the tool:**

| how it was started | what the button does |
|---|---|
| the shipped `docker-compose.yml` (`restart: unless-stopped`) | the container stops and the daemon starts it again within a second |
| docker **without** a restart policy — your own compose file, `docker run` without `--restart`, another orchestrator | the container stops and **stays stopped** until somebody starts it on the host |
| by hand (`node backend/v2/server.mjs`) | the process ends; starting it again is your job |

The middle row is the dangerous one: from the browser it is indistinguishable from the first, the web UI goes down with the process, and without access to the host there is nothing left to undo it from. The tool does **not** try to work out which case it is in — Docker gives a container no way to read its own restart policy, and the one thing that could answer it is the socket that is deliberately not mounted. So the condition is *named* rather than checked: the confirmation dialog spells it out before anything happens, and when the page's wait for the server runs out it says that nothing appears to have restarted the container, what to run on the host, and to add a restart policy so the button works next time. That message survives a page reload. If you keep the restart button but not the shipped compose file, add the policy:

```yaml
services:
  poe-price-tool:
    restart: unless-stopped
```

Every override can be **removed** again (the UI's *reset*), which puts the setting back on the compose value it was started with, or on the built-in default if there was none — the first bad value never needs an SSH session.

**Boot quarantine — the restart loop that cannot happen.** An override that kills the process at startup would restart forever and leave no web UI to undo it. So applying the file is bracketed: `overrides.applying` is written **before** the values reach the environment and deleted the moment the server is listening. The marker **counts, it does not switch**: what it can observe is "the last start did not reach `listen`" — never "the overrides were to blame". The whole expensive boot sits inside that window (the engine instances load serially, the data refresher initialises), and so does everything from outside that can end a process in it — a `docker compose restart` typed at the wrong second, a host reboot, an out-of-memory kill — while only validated values reach the file through the UI. So the marker carries the number of consecutive failed starts:

| starts in a row that never listened | what the next start does |
|---|---|
| 1 | applies the overrides again and says so in the log (`did not reach 'listening' (1 of 2 …)`) |
| 2 | moves the file to `overrides.rejected.json` and boots on the compose/default configuration |

A start that reaches `listen` deletes the marker and with it the count, so two failures a week apart never add up. Nothing is lost either way: inspect the rejected file and put it back by hand if the problem was elsewhere ([runbooks.md → The overrides were quarantined](runbooks.md#the-overrides-were-quarantined)). Saving anything on the settings page **clears the quarantine alarm**: the alarm describes a file that was put aside, and that write replaces it. The parked `overrides.rejected.json` stays where it is — nothing but you puts it back.

> **One `/config` volume belongs to exactly one instance.** Two containers on the same volume share this marker (and the override file, and the language store), so they count each other's boots as their own failures — two instances started together are enough to quarantine a perfectly good configuration. There is deliberately no lock (it would bring its own stale-holder problem, for a deployment mistake). Give each instance its own volume.

**What can be set** is a fixed allow-list, validated by type on the way in (a value that fails is refused with a `400`, not written). In four groups by what they control (the page draws three blocks: takes effect immediately, needs a restart, and the last group below as a block of its own):

- *Identity and display* — `POE_APP_NAME`, `POE_LEAGUE`, `POE_LANG_DEFAULT`, `POE_PATCH_VERSION`, `POE_MAX_LISTINGS`, `POE_NETWORTH_DEBUG`, `POE_CD_RATIO`. `POE_PATCH_VERSION` is the documented repair for a patch lookup that has failed, settable here so the escape hatch does not need an SSH session. It is **empty by default** (the version is looked up), takes effect at the **next check** without a restart, and is validated with the generator's own pattern, so the form cannot accept a value the next start would refuse. Clearing it again after the following patch: [runbooks.md → The patch lookup failed](runbooks.md#the-patch-lookup-failed), step 4.
- *The background jobs, as switches* — `POE_NETWORTH_AUTOSYNC`, `POE_FAUSTUS_DISABLED`, `POE_CORPSE_DISABLED`, `POE_DATA_REFRESH_DISABLED`, `POE_REFERENCE_DISABLED`. Their dangerous direction is "on", which is also the default and is written on the label, so they stay in the ordinary groups. `POE_RELEASE_CHECK_DISABLED` is a switch of the same kind but not dangerous either way: "on" costs one request a day to GitHub and nothing towards the trade API.
- *Bars and limits that cost nobody a request* — `POE_NETWORTH_LIST_TTL_MS`, `POE_FAUSTUS_TTL_MS`, `POE_SOURCE_STALE_MS`, `POE_NINJA_MAX_AGE_MS`, `POE_DATA_STALE_TICKS`, `POE_GAP_LOG_MAX`, `POE_GAP_LOG_TEXT_MAX`, `POE_UPDATE_HEARTBEAT_MAX_AGE_MS`, and the farm-session display thresholds `POE_SESSION_RATE_MIN_MS`, `POE_SESSION_TOP_N`, `POE_SESSION_LIST_MAX`, `POE_SESSION_BASELINE_MAX_AGE_MS` (the two that shape stored sessions, how many are kept and how long an ended one waits, are environment only, and so are the two of the game sessions), and the two bars of the Net-Worth uncertainty marker, `POE_NETWORTH_THIN_TURNOVER_C` and `POE_NETWORTH_CORPSE_MIN_LISTINGS` (they only mark rows; effective after a restart). `POE_SOURCE_STALE_MS` takes effect without a restart: the server sends every open page the source status, and its C:D tile when that came from poe.ninja, again right after the change.
- *How often this tool asks other people's servers* (its own block, above) — `POE_NETWORTH_SYNC_INTERVAL_MS`, `POE_NETWORTH_COOLDOWN_MS`, `POE_CORPSE_BUDGET_PER_HOUR`, `POE_CORPSE_INTERVAL_MS`, `POE_CORPSE_TTL_MS`, `POE_FAUSTUS_REFRESH_MS`, `POE_CD_REFRESH_MS`, `POE_DATA_REFRESH_MS`, `POE_NINJA_MAP_TTL_MS`, `POE_NETWORTH_SKIP_TIER_MAPS`. The last one is the only switch in that block: it is **on by default** and passes over the per-tier pages of the map stash, which is 14 of 43 sub-tabs on the account it was measured on — normal maps carry no price here, so what it saves is requests and what it costs is nothing that was ever part of the number. Turning it **off** reads the whole map stash and makes a full round markedly longer.

The list itself is served by the endpoint (`backend/v2/config-overrides.mjs`), so the page and the server cannot disagree about it, and a test compares the names above against that list. The **defaults and ranges** of every numeric row are read out of `numeric-settings.mjs`, the same table the server reads the value through: one answer to "what is the default" and one to "what is allowed", and the allow-list may only narrow a range for the browser path, never widen it.

**What can never be set**, and why:

- `POE_USERS` — rooms, the per-tab net-worth store, the credential file and the language mapping are all keyed by those names. One click in a browser must not be able to orphan all of that. It stays in compose.
- **Paths and ports** — a wrong one takes the tool off the air with nothing left to fix it from.
- `POE_PRICE_CHECK_DISABLED`, `POE_REFERENCE_ON_CONNECT_DISABLED` and `POE_LEAGUE_LIST_DISABLED` — they exist for the test suite and for a deployment that deliberately runs without the price check or without client-triggered reference traffic. As checkboxes they would switch off the tool's main feature and the rail beside it, and every card afterwards would be unpriced with nothing on the page saying why.
- `POE_TRADE_AUDIT` and `POE_TRADE_AUDIT_THRESHOLD` — the rate-limit audit is the observability that exists *because* of the two bans; a page must not be able to blind the tool to how full its rate-limit windows are. The threshold follows its switch: it is a fraction with no upper bound, so a `2` typed into a form would silence the audit as effectively as the switch, and without saying so.
- `POE_FAUSTUS_UNION_HOURS` — the one numeric setting with no default of its own: unset means "faustus.mjs decides" (8), the normal state, so the page could not answer *what do I get if I clear this*, the one thing every other row can. It also multiplies the CDN fetches of every refresh pass, which makes compose the safer home for it.
- `POE_NINJA_FAIL_LOG_MS` — it only decides how often a failing poe.ninja request shows up in the container log, which nobody reads from the page. An operator setting, so it stays in compose.
- **Anything secret.** No POESESSID, no account name, no password. Not settable, and not *shown* either: the read-only block that lists the remaining effective settings is filtered by name, and a test walks the entire response and fails on any key that could name a credential.

### Which version is running

The admin area's update block prints the commit the running image was built from. Docker has no idea what git thinks and the build context does not even contain `.git`, so the only source is whoever starts the build — the `BUILD_COMMIT` build argument (`BUILD_COMMIT=$(git rev-parse --short HEAD) docker compose up -d --build`, see [runbooks.md → Update procedure](runbooks.md#update-procedure)). Without it the block says **unknown**, on purpose: a plausible made-up value is worse than no value for the one question every update starts with. `deploy/host-update.sh` passes it by itself, so an update through the button always records its commit.

Beside the commit the server knows its **version number**, the `"version"` field of the `package.json` the image carries (the `Dockerfile` copies it into the runtime image). When that file is missing or has no `x.y.z` version, the Releases block on the settings page says **unknown** instead of guessing. The same number is in the User-Agent of every request the tool sends in its own name, `poe-price-tool/<version> (<purpose>)`, with `unknown` in place of a version it cannot read; the trade searches and stash reads send a browser-like agent instead (README, section [What it does in the background](../README.md#what-it-does-in-the-background)).

#### Release check

Once a day (24 hours after the last check, whatever it found, success or failure; first check about 10 minutes after a start with no state) the backend asks `https://api.github.com/repos/<POE_RELEASE_REPO>/releases/latest` for the latest release and compares its tag with the installed version. The tag must look like `1.2.3` or `v1.2.3`; anything else — a pre-release suffix, four numbers, no tag — is an answer that cannot be read, not a silent "current".

- **What it sends:** a GET with `Accept: application/vnd.github+json`, an `If-None-Match` with the stored `ETag`, and the installed version inside the User-Agent (`poe-price-tool/<version> (release check)`). Nothing else, no credentials. A request that gets no answer within 10 seconds counts as unreachable.
- **What comes of it:** when the latest release is newer, every page shows one line saying so and the settings page names both versions and links the release page. Equal or older (a development build) is silent; the manual check then says "up to date". A failure is silent when automatic; the last good answer stays in `release-check.json`. Whether a release is newer is worked out each time the status is read, so a freshly updated server stops reporting it at boot.
- **It never installs anything.** Updating stays the [update procedure](runbooks.md#update-procedure).
- **Turn it off:** `POE_RELEASE_CHECK_DISABLED=1`, or the switch in the admin area (read at each tick, so it takes effect live). The manual button works either way.
- **Fork:** `POE_RELEASE_REPO` points the check at another repository.
- **Wire format:** `release-status` message and `GET /release-status` in `backend/v2/frontend/PROTOCOL.md`.

### Update button (`deploy/host-update.sh`)

The admin area has an **Update** block below the restart button. It pulls the newest code on the server and rebuilds the container — but only if you have installed a small script on the host first ([runbooks.md → Install the update script](runbooks.md#install-the-update-script)). **Without that script nothing about this installation changes**: the button is visible, disabled, and says what would have to happen. Nothing new is written into `/config`, nothing new runs at startup.

The button exists for the case where you are not at a shell. **The normal way to update stays [`git pull && docker compose up -d --build`](runbooks.md#update-procedure) on the server**; the button runs only those two fixed commands, so it cannot do league-start steps or review a diff, and the league-start and manual data-refresh steps have no button and are not going to get one.

#### Why it works this way round, and not with the Docker socket

The restart button can end its own process; the container supervisor brings it back. An update cannot work like that: `git pull && docker compose up -d --build` needs a checkout and a Docker daemon, and both live on the host. Bind-mounting `/var/run/docker.sock` into the container is deliberately not done: **the Docker socket is unauthenticated root on the host.** Anything that can reach it can start a container with `/` bind-mounted and own the machine, and it would be handed to a tool with **no authentication at all** (LAN by design), whose admin area sits behind one plaintext password whose default is published in a public repository, and which parses foreign text off the internet all day.

So the direction is reversed: **the container asks, the host decides.**

```
  container                       /config volume                 host (cron)
  ─────────                       ──────────────                 ───────────
  POST /update-request  ──────▶   update-request     ──────▶     host-update.sh
                                                                   ├ writes heartbeat
                                                                   ├ deletes the request
                                                                   ├ git pull --ff-only
                                                                   └ docker compose up -d --build
  GET /update-status    ◀──────   update-heartbeat   ◀──────     (every run)
                        ◀──────   update-result      ◀──────     (after a run)
```

**The security property everything hangs on:** the script reads the request file only to learn *that* somebody asked, never *what* to do. Directory and command are constants at the head of the script. No branch, no tag, no path, no argument travels out of that file into a command — it is never sourced, expanded or evaluated. Writing that file is exactly what an attacker who reached the admin area can do, and the most it can achieve is "the host rebuilds the code the host already has". The moment a value from the file reached the command line, the request would become an instruction, and that would be remote code execution on the host. If you edit the script, keep it that way; the same warning is in its header.

**The same argument for files:** the shared directory is writable by the container and the script runs as root over it, so the script trusts no *name* in there to be what it looks like. It stages nothing inside that directory (a predictable path there plus a root writer is a way to have root overwrite a file somewhere else, and a FIFO there is a way to hang the updater for good), it keeps its lock outside it (in there, the container could occupy the lock once and no update would ever run again), and anything in there that exists but is not a plain file stops the run with a message instead of being worked around. Publishing into the directory is a `rename()`, which follows no symlink and opens nothing. The three conditions a host has to meet before installing it are in [runbooks.md → Install the update script](runbooks.md#install-the-update-script).

#### What the script does, exactly

- **Refuses to run** if the checkout sits inside the shared directory (or is the same directory), if a directory it is about to send to the Docker daemon is not excluded by `.dockerignore`, or if it cannot create its own work directory outside the shared one — the install preconditions, checked rather than only written down.
- **Writes its heartbeat on every run that gets past the precondition checks** — including the runs that find nothing to do, and including the ones that exit immediately because a build is already running. That is what the admin area reads "an updater is installed" from. (With a systemd `Type=oneshot` timer there are no such runs during a build; see [runbooks.md → Install the update script](runbooks.md#install-the-update-script).)
- **Does nothing without a request.** There is no daily pull, no "while we are here anyway". Nobody presses, nothing updates.
- **Stops with a message if anything in the shared directory is not a plain file** — a symlink, a directory or a pipe where one of its three files belongs. That is somebody having been in the volume, and the run says so instead of continuing.
- **Deletes the request before it starts working.** A failed build is not retried every five minutes for as long as nobody looks; a failure is reported and waits for a human to press again.
- **Takes a lock** (`update.lock`, a directory — `mkdir` is atomic) so two cron ticks can never build at the same time. The lock lives in the script's work directory, not in the shared one.
- **Reports a lock nobody is holding.** If a run is killed hard — a host reboot in the middle of a build — the lock stays behind and every later run exits at it. Once it is older than two hours (far past any build), the script writes that into the heartbeat and exits non-zero on every run, and the admin area disables the button and says the updater is stuck. It does **not** break the lock by itself: that would mean guessing that the run holding it is dead, and guessing wrong means two builds of the same image at once ([runbooks.md → The updater is stuck](runbooks.md#the-updater-is-stuck)).
- **Runs exactly two commands** in `REPO_DIR`: `git pull --ff-only` and `docker compose up -d --build`, with `BUILD_COMMIT` read from the checkout after the pull so the new image knows its own commit.
- **Writes the result**: outcome, start and finish time, and the tail of the output (4 000 bytes), staged in the work directory and renamed into place, so a reader never sees half a file.

#### Reading it back in the browser

The admin area shows the last result and, on a failure, the end of the output. That excerpt is **text from the host**, so it is treated as foreign: bounded on the way in, put into the page as text and never as markup, and run through the same name filter `/config-view` uses — a line that names a credential is **dropped** and replaced by a visible marker, and credentials inside a URL (`https://user:token@host/…`, which a failing `git` will happily print) are masked. **That filter is not a guarantee, and the page says so under the excerpt.** It catches names and shapes; a **bare token on a line that names nothing and forms no URL** — an id echoed by a build step, a key printed on its own — goes straight through. Treat the excerpt as text that may still hold a secret.

"An updater is installed" means: a heartbeat that is **less than 20 minutes** old (`POE_UPDATE_HEARTBEAT_MAX_AGE_MS`), at the recommended 5-minute schedule three missed runs plus a cushion for a busy host or a clock a minute off. A missing heartbeat is reported as **"not set up"**, never as "broken" — the tool cannot tell a script that was never installed from one that was removed an hour ago. When the page has waited 15 minutes without an answer: [runbooks.md → The update button gets no answer](runbooks.md#the-update-button-gets-no-answer).

### Net-Worth-Tracker (`/networth.html`)

Reads the whole stash via the legacy `character-window/get-stash-items` endpoint using the **POESESSID** session cookie (ToS gray area, personal use only — knowingly accepted).

<a id="stash-api-language"></a>
**Stash API language — measured, 2026-08-10.** The tracker joins GGG's `typeLine` against the English `refName` of the item database (`backend/v2/networth/normalize.mjs`), so a localized response would break the whole valuation. It does not: the API answers **English regardless of language settings**. Verified by switching all three in turn and watching a full refresher cycle after each:

| Setting | Result |
|---|---|
| Game client → German, account still English | a full cycle, nothing changed |
| Account *Preferred Language* → German **and** the site to `de.pathofexile.com` | 18 of 18 tabs re-fetched, **870 item names, zero carrying German characters** |

That matches the code and GGG's own wording: the client sends no `Accept-Language` (`backend/v2/networth/stash-client.mjs`), and GGG describes the account preference as governing "automated messages and emails", not API payloads. So a German player needs **no translation step** here. Two caveats: this is one account, and GGG could start localizing these payloads without notice. The symptom would be unmistakable — the assignment rate collapses for that user and the unpriced list fills with German names — and it is visible per user in the admin area's gap view.

**Folder tabs (Unique Collection, Map tab).** The legacy endpoint always answers with an EMPTY `items` array for these — their items live in sub-folders it has no address for (measured: `subIndex=0/1` and `tabs=1` return byte-identical `items=0`; passing the tab id yields HTTP 404). Those two types therefore go through the site's newer stash endpoint, same cookie session, two levels deep:

    GET /api/stash/<league>/<tabId>            -> { stash: { children: [{ id, … }] } }
    GET /api/stash/<league>/<tabId>/<childId>  -> { stash: { items: [ … ] } }

(`/api/stash/<league>` without an id answers 403, so the tab LIST still comes from the legacy endpoint.) One such tab costs `1 + N` requests — the Unique Collection tab has 17 sub-folders — through the same sequential `requestUrl()` as everything else, so the rate-limit headers, the backoff and the timeout all apply unchanged. This endpoint is undocumented: anything unexpected degrades to "tab empty" and logs a warning; only auth/rate-limit propagate (cookie and ban protection).

<a id="folder-subtab-shape"></a>
**Every sub-tab is read except the map stash's tier pages, and the log says which those were.** A folder tab is read whole — every child the parent response lists and that carries an `id` — with one exception. On 2026-08-13 a *name pattern* passed over the map stash's per-tier sub-folders (they hold only normal maps, which are never priced). GGG names those children **`"1"`, `"2"`, …, page numbers**, so the pattern matched all 39 of them and the whole map stash went unread, `Unique Maps` and `Special Maps` with it, for about 165 chaos of net worth that the history then recorded as missing; it was reverted the same day (`docs/bugs.md`, B19). The measurement that replaced it answered on **2026-08-19**: the children carry `metadata.map.section`, GGG's own label — `unique`, `special` or `tier<N>`. The skip runs on that field: **only an explicit `tier<N>` is passed over**, so a missing `metadata`, an unrecognised section or a stash shaped differently is read. The worst a misreading can do is cost requests. On the account it was measured on that is 14 of 43 sub-tabs, one derived spacing each.

It is a setting — `POE_NETWORTH_SKIP_TIER_MAPS`, on by default, `0` reads the whole map stash — and not a silent one. Every walk that passes anything over says so in the ordinary log, without a debug flag:

    [stash-client] folder tab "Maps": 14 of 43 sub-tabs not read — GGG lists
    them as tier16 x2, tier11, tier12, … , i.e. pages of normal maps, which
    carry no price. That saves 14 of the 44 requests this tab costs.
    POE_NETWORTH_SKIP_TIER_MAPS=0 reads them too.

It deletes nothing that was ever a priced number — normal maps are unpriced stock either way, so what changes is that they stop appearing in the *unpriced* list — and it says out loud what it left out.

**The shape measurement.** The first time a process walks a given folder tab it prints the children exactly as GGG returned them — one line per folder tab per process, never per walk, at no request because the parent response is already in hand:

    [stash-client] folder tab "Maps" (MapStash) sub-tab shape as GGG returns it,
    once per process: 39 children, entry fields: id,parent,name,type,metadata —
    parent response keys: stash; parent stash fields: …; parent metadata: {…} —
    "1" type=MapStash metadata={…}, "2" type=MapStash metadata={…}, …

It reports the union of the child entry field names, each child's `name`, `type` and the **content** of its `metadata` as JSON, every other field of a child by value — so a `folder`, `page` or sort field nobody predicted shows up by itself — and the parent's own fields and `metadata`, in case the structure is explained a level up. `id` and `parent` are named but never printed: they are opaque addressing tokens. Everything is foreign data, so every value goes through the same credential filter that guards `/config-view` (a key that could name a credential prints as `[redacted]`), control characters are stripped, and each part is length-capped. It is there to show which **section** a child belongs to: `name` is a page number and `type` is the parent's type repeated on every child (both measured, neither an answer). Guessing is not on the list.

**The POESESSID is needed for this one feature only.** The price check works without it (see "POESESSID" under "Single-league coupling"), so the cookie is optional for the tool as a whole and required just for the Net-Worth tracker. Credentials per user live in `/config/networth-users.json` (in the `./config` volume, **never in the repo**, `chmod 600`):

    {
      "player1":  { "accountName": "YourAccountName#1234",  "poesessid": "<cookie value>" },
      "player2": { "accountName": "OtherAccountName#5678", "poesessid": "<cookie value>" }
    }

- The key of each entry must match a name in `POE_USERS` (the player's room). Multiple players = multiple entries, each with its own, separate snapshots.
- **`accountName` must be the full name including the discriminator**, e.g. `Name#1234` — the bare name without `#1234` is the most common cause of `HTTP 403 (forbidden)` (you can only read your own stash, and the game matches on the full name). If the name is definitely right and it still 403s, one untested possibility is the account's profile privacy setting — this has only ever been run against a **public** profile, so whether a private one can read its own stash through this endpoint is unknown here.
- The file is **re-read every auto-sync round** — adding a player or rotating a cookie needs no restart.
- The container runs as UID 1000 (`node`): the file must be **readable** by that UID, otherwise the background sync fails with `EACCES: permission denied`.
- **Why the cookie expires so often:** every new login invalidates the previous POESESSID — including logging in through your PoE account on a third-party site (Filterblade and similar). A paused user after such a login is expected behaviour, not a fault of the sync. **POESESSID lifecycle (per community reports/web, not officially documented by GGG):** logging out invalidates the POESESSID, and logging back in issues a fresh one, so after any re-login (browser, another device, session expiry) the old cookie stops working and `networth-users.json` needs the new value. On expiry the background sync logs a 401/403 and pauses that user until the cookie is renewed.
- **Preferred way to set/renew credentials: the UI.** The "Sync settings" section of the settings page (`/settings.html`; the Net Worth page links to it from a button and from its sync status line) lets the current user set `accountName` + `POESESSID` themselves. It writes the same `networth-users.json` atomically with `600`, touching only that user's entry, and the refresher picks the change up on its next tick. The stored POESESSID is never sent back to the browser in any form (`GET /networth/credentials` returns account name + sync state only). The sync state per user (`ok` / `expired` / `cooldown` / `missing`) is in the global status line: the Net Worth page and the settings page show every state in their own wording, the History and Price Check pages show only `expired` ("Background sync is paused: the stored POESESSID has expired. Renew it on the settings page.") and leave the line empty otherwise.
- Alternative via env: `POE_SESSID` + `POE_NETWORTH_ACCOUNT` (+ `POE_NETWORTH_USER`). If `POE_SESSID` is set for a user, it keeps winning over the file — a cookie saved in the UI won't take effect for that user until the env var is removed. The credentials file path itself is redirectable via `POE_NETWORTH_CONFIG` (default `/config/networth-users.json`).

Getting the cookie, file permissions, and writing or rotating it over SSH when the app itself is down: [runbooks.md → Net-Worth credentials](runbooks.md#net-worth-credentials).

**Architecture — per-tab store + continuous auto-refresher (the only sync path, 24/7):** every stash tab is written immediately to `POE_NETWORTH_STORE` (`/config/networth-store.json`) as its own entry, so the store is never all-or-nothing. A background auto-refresher (enabled by default, `POE_NETWORTH_AUTOSYNC=0` disables it) continuously walks the configured users' tabs **one tab per tick** (`POE_NETWORTH_SYNC_INTERVAL_MS`, default 30s) — one tick is one tab for ONE user, taken round-robin, so the tick rate is the whole load and does not multiply with the number of users — always picking that user's stalest tab next. The stash-tab list itself is cached for `POE_NETWORTH_LIST_TTL_MS` (default 15min). On a 429 **every** user backs off for `POE_NETWORTH_COOLDOWN_MS` (default 10min), or for the `Retry-After` GGG named if that is longer (see "The stash path has its own budget").

**Sync follows the game.** A hotkey daemon new enough reports whether the game runs on its machine (it looks for a window of `poe_window_class` with `xdotool`, and says "not running" only after it has found that window once on its display; `[presence]` in its `config.toml`): every five minutes while the game is not running, every minute while it runs or the daemon cannot tell, and at once on a change. The refresher uses that only to decide WHOSE tab is read on a tick, never to read more: one step per tick stays the rule, and the stash pacer's spacing applies to every request. If some players' games run and others' do not, the others yield their ticks and get every `POE_NETWORTH_IDLE_EVERY`-th one (default 10). If no game runs anywhere, only every `POE_NETWORTH_IDLE_EVERY`-th tick reads a tab (`POE_NETWORTH_IDLE_REST=1`: none, and players whose game is not running are not read at all). A player whose game just stopped keeps the normal pace until each of their tabs was read once since then, at most `POE_SYNC_AFTER_GAME_MAX_MS` (1 h), so the loot of the last minutes arrives at the playing pace. A player whose cookie has expired still counts as playing while their game runs, and during that hold, which then lasts the full `POE_SYNC_AFTER_GAME_MAX_MS` because their tabs cannot be read: their ticks lapse and are not handed to the others, so players whose game is not running keep every `POE_NETWORTH_IDLE_EVERY`-th tick as if nobody played. A player without such a daemon, a daemon that cannot tell (no `xdotool`, no display, a window class it has never found) or that stopped reporting, and the first minutes after a server start all count as "unknown", which means the normal pace. The status line says when the sync yields or rests ("Sync yields: your game is not running — about one tab every 5 min"), and the server log has one `[networth-refresher] pace … -> …` line when the distribution changes. What the stash API tolerates at a league launch is not documented: GGG's developer documentation (<https://www.pathofexile.com/developer/docs>, as of 2026-11-03) calls its rate limits dynamic and subject to change at any time, and says nothing about a league launch. The refresher behaves there as at any other time; this only moves or drops requests, and a 429 there stops the sync of every player for `POE_NETWORTH_COOLDOWN_MS` (or a longer `Retry-After`), playing or not.

**A session round.** When a farm or game session of a player starts or ends (see "Farm sessions" under the History page), the refresher reads each of that player's live tabs once from that moment before it reads one twice, and holds the tab-list refresh back until it is done; the sync status (`networth-sync-status`, field `sessionRound`) says how many of the tabs are read. This only orders the steps the player gets anyway: no extra tick, no shorter interval, the rules above unchanged. The stalest-first order already reads those tabs first, so the gain is the list refresh that waits, and that the round can be seen. One round per player at a time; a start or end at a later moment replaces it (a game session's end, dated back to when the game stopped, does not replace a round from a later moment, which reads every tab after the stop as well).

**Why a drip-feed and no manual full-scan button:** a large stash (example: ~115 tabs) fetched back-to-back in one burst runs straight into GGG's trade-API rate limit (429, aborts partway). The auto-refresher spreads requests over time (one tab/~30s) instead: a full stash of that size fills in over one refresher cycle (~115 tabs × 30s ≈ 1h), then stays fresh in the background indefinitely.

The `/networth.html` page itself is **read-only** — it displays whatever the background auto-sync has built up so far, with no button that starts a sync. A counter above the list reads `{recent}/{total} tabs synced in the last 10 min · oldest tab synced {mins} min ago`; the 10-minute window is fixed, not derived from the sync interval. Priced: stackables (currency/fragments/essences/scarabs/fossils/resonators/oils/tattoos/omens/delirium orbs/artifacts, via Faustus first), div cards, unique items, gems, beasts, incubators, vials, Maven's Invitations, and itemised corpses (via the Trade API); **rare/magic gear and non-unique maps are deliberately out of scope** and show up as "skipped". Full source routing and the rules behind each category: [docs/pricing-logic.md](pricing-logic.md).

A stash tab in the sidebar that is worth nothing says **why**: hovering the row gives `N priced · N unpriced · N skipped`, and the row itself carries a `⨯N` when everything that arrived was skipped, or a `∅` when nothing arrived at all — "0c" alone cannot distinguish them (`docs/bugs.md`, B7). The numbers come from the per-tab store.

#### When the refresher goes quiet

First check the ban banner: an active **trade-API ban** stops this refresher as well, and the status line says so ("the GGG trade API has blocked this app — stash syncing pauses with it until …"). That is a quiet refresher doing the right thing; there is nothing to diagnose and nothing to restart.

Otherwise: **one tick does one request**, and a tick is guarded so only one is ever in flight. A **folder tab** (Unique/Map stash) costs `1 + N` requests, so it is `1 + N` ticks: one sub-tab per turn, with every other tab and every other user taking their turns in between as usual. **A folder tab does not hold the refresher for its whole walk.** Held inside ONE step, a walk occupies the global busy flag for all of it: measured on the container on 2026-08-11 at a 24 s spacing, the map stash held its step for **913 s** (38 requests: the sub-tab list plus ~37 sub-tabs) and the unique stash for **457 s** (19 = 1 + 18), and at the 80 s an unauthenticated rule set derives the map stash would have held it for **50 minutes**, with nothing else moving, other users included. The walk is a piece of state the refresher puts down between ticks: **the same requests, in the same order, at the same pace**, spread over their own turns. What one folder tab costs another user is one step.

These observations report it, all of them read-only:

| Where | What it says | How often it fires |
|---|---|---|
| `networth-sync-status` (WS) | `lastTab` — when a tab was last written for this user, and which. `current` — the step in flight: phase, since when, the tab name when it belongs to this user, and `child`/`childTotal` inside a folder tab | on connect and on every state change. Nothing is pushed *during* a step — reload the page to take a fresh reading |
| `networth-sync-status` (WS) | `folderTab` — the folder tab being walked right now: which one, `done` of `total` sub-tabs, and since when. **Answerable between ticks**, which `current` is not: a walk is not a step, so most of the time there is no step to report | on connect and on every state change, while a walk is open |
| `[stash-client] folder tab "X" (MapStash): reading sub-tabs` | a folder tab has started | once per folder-tab turn, i.e. once per full round of the round-robin |
| `[stash-client] folder tab "X" (MapStash) sub-tab shape as GGG returns it, once per process: N children, entry fields: … — "…" type=… metadata={…}` | what the children really are: the field names, each child's name, type and `metadata` content, any further field by value, and the parent's own fields and metadata. Credential-filtered, control characters stripped, length-capped. It decides nothing itself — the rule that reads `metadata.map.section` is a separate module (`networth/map-sections.mjs`) | **once per folder tab per process**, never per walk. It costs no request — the response was already in hand |
| `[stash-client] folder tab "X" (MapStash) yielded 0 items — N sub-tabs, …` | a folder tab came back empty **without failing**. Names the sub-tab count, how many of them answered in the expected shape, how many were non-empty, and how many carry children of their own | never while folder tabs deliver, which is the normal state (`docs/bugs.md`, B7). One line per turn of a folder tab that does come back empty |
| `[networth-refresher] folder tab "X" (index N) for <user>: M sub-tabs over S steps in Ts` | the closing bracket of a walk, the counterpart to the `still busy` pair a folder tab does not produce. Says `(K of them not read — see the line above)` when the tier-page skip was in force | once per folder-tab turn |
| `[stash-client] folder tab "X": K of M sub-tabs not read — GGG lists them as tier16 x2, …` | the tier pages of the map stash were passed over (`POE_NETWORTH_SKIP_TIER_MAPS`, on by default). Unconditional: value left out of a tab on purpose has to be visible without a debug flag | once per folder-tab turn, while the skip is on |
| `[networth-refresher] still busy: tab "X" … has been running for Ns` | one step has held the tick longer than `POE_NETWORTH_SLOW_STEP_MS` (2 min). A second line follows when it finally returns | **never in normal operation.** A step is one request, so this means one genuinely stuck step, one line, not one per skipped tick |
| `[stash-client] folder tab "X" (MapStash) was NOT read in full — N sub-tabs, …` | a walk finished, nothing threw, and a sub-tab still said nothing about itself: it answered HTTP 200 with a body carrying no items array, or GGG listed an entry the walk cannot address. The same counts as the `yielded 0 items` line, plus how many answered with something else and how many could not be addressed. **Nothing is written** — the tab keeps the contents it was last really read with | never while folder tabs deliver; one line per folder-tab turn that hits it |
| `[networth-refresher] a tab of <user> was NOT read and is left as it was stored (no point is recorded from this step): …` | the refresher's end of the same thing, and it covers ordinary tabs too: GGG answered without contents, so the tab is not overwritten and no history point comes out of this step | never in normal operation; one line per affected turn |
| `[networth-history] the stash tabs <user> is summed over changed (N now, M before) — one point is skipped …` | the snapshot's set of stash tabs is not the one the last point was summed over: a tab was pruned out of the store, or one that had never been read has just been read. One point is skipped and the item diff starts over, because a tab appearing or disappearing is not stock moving | on a genuine tab deletion or a first reading; otherwise never |
| `[networth-history] recording for <user> over N of M tabs — K have been tried and never yielded a reading` | points are being written over less than the whole account. Allowed on purpose — a tab that never becomes readable must not stop the series for good, and its absence is then a constant in every point rather than a dip in one — but never silently. A `every tab of <user> reads again` line follows when it clears | on the transition only, not per tab |

**No watchdog releases a step, and none is needed for a folder tab.** Forcing the busy flag back would put a second request against GGG in flight next to the first and break the strict sequentiality the whole rate-limit discipline rests on; this project has a ban history. A step is one request (`docs/bugs.md`, B5).

**A half-read folder tab is never written to the store.** The walk lives in the refresher's memory, so the previous *complete* contents of the tab keep counting towards the snapshot until the new reading is finished, and a restart in the middle of a walk walks it again from the beginning. A failure mid-walk drops the walk and writes nothing; a 429 keeps it, so the cooldown costs the remaining sub-tabs rather than all of them — and it costs the refused sub-tab too, which the walk goes back to rather than stepping over (a walk with a hole in it is not written at all). **"Half-read" includes a walk that finished without answers:** a sub-tab can reply HTTP 200 with a body that carries no items array — the shape B7 measured, and the only way it could name for a full tab to come back empty with no error line anywhere. Such a walk is not accepted as the tab: a *subset* would leave the store with a tab missing items nobody had moved, and the history would record that as stock leaving the stash (`docs/bugs.md`, B2). The walk says so in the log and writes nothing.

**A stored tab is only dropped when two consecutive tab lists agree it is gone** (one bad response must not delete a user's entire stored stash, `docs/bugs.md` B2):

| Line | What happened |
|---|---|
| `[networth-store] a live tab list of L would drop N of M stored tabs for <user> — held back until a second list agrees` | one short (or empty) answer. **Nothing was deleted.** If the next list is whole again, nothing ever will be |
| `[networth-store] pruning N of M stored tabs for <user> (live tab list: L) — two consecutive lists agree they are gone` | the drop was carried out, for the tabs BOTH lists were missing |

The price of the second opinion is that a tab you really did delete in game keeps showing its stored value for one more list interval (`POE_NETWORTH_LIST_TTL_MS`, 15 min by default); it costs no extra request, because the second list is the one the refresher fetches on that schedule anyway. There is deliberately **no threshold** on "how much shorter": nobody has measured how often GGG answers short.

#### Uncertain prices

The table's Confidence column marks prices the valuation knows to be guessed or thinly evidenced, and the total says how much of it rests on them; nothing is subtracted. What each mark means and why: [pricing-logic.md](pricing-logic.md#uncertain-prices--marked-and-still-counted). The two bars are `POE_NETWORTH_THIN_TURNOVER_C` and `POE_NETWORTH_CORPSE_MIN_LISTINGS`. Data stored before these fields existed reads as unmarked until it is written again (how long that takes per source: same section of pricing-logic.md).

#### Listed below market

The block under the table lists the player's own price notes (`~price` or `~b/o`, the item's or its tab's) in premium tabs that are under the tool's market value (the 100 biggest losses, and how many more), by the buyer-whisper rule: `POE_WHISPER_LOW_RATIO` decides it for both, so changing it moves both. The note is read from the stash answer the refresher already fetches and kept in `networth-store.json` (`listed` per tab, with the item's cell and its market value); no extra request is made, no notification is sent, and nothing goes to the daemon. A tab stored before the field existed has no notes until the refresher reads it again (one lap); the file keeps `schema_version: 2`, so an older release still reads it. A note in divine needs a live Chaos:Divine rate: while the rate is the fallback (`POE_CD_RATIO`) or stale, such notes are counted as not compared. Rule and readings: [pricing-logic.md](pricing-logic.md#listed-below-market).

### History page (`/history.html`)

The History page draws the net-worth series over time — a trend chart plus the stock movements behind it ("what came in, what went out") — and measures farm sessions (below). It has no data source of its own: it reads what the Net-Worth auto-refresher records as it walks the stash, over two read-only endpoints for the chart (`/networth-trend`, `/networth-events`) and the session endpoints (`/networth-sessions`, `/networth-session/start|end|discard`), all with identity via the same `ppt_user` cookie. Selectable ranges are 1h, 6h, 24h, 7d and 14d. A further endpoint, `/networth-detail` (per-point item detail), exists on the server but is not called by the current frontend.

**What the chart is measured in.** Divine, and every point is converted with **the C:D rate it was recorded at** — never with today's, which is why a figure on this page cannot change once it has been recorded. One consequence, before it gets reported as a bug: when the divine grows more expensive faster than the stash grows, the curve falls although nothing left the stash. The rate of the shown window is therefore on screen — as a `C:D` row in the rail and as a pale line across the plot (own scale, no second axis) — and an **(i)** at the chart explains it on request. A window in which no point carries a rate at all is labelled in chaos instead of guessing one; see [`pricing-logic.md`](pricing-logic.md#what-a-figure-on-the-history-page-means).

**Where the data lives.** Three files in the `/config` volume:

- **`networth-history.ndjson`** (`POE_NETWORTH_HISTORY`) — the series itself, one JSON object per line, append-only. Each point carries the total in chaos, the C:D rate **of that moment** (so an old point is never re-derived with today's rate), and the biggest item movers since the previous point. Lines recorded before mid-2026 also hold a per-tab chaos breakdown; it is neither read nor written, and such lines are still read normally until retention drops them.
- **`networth-history-items.json`** — a sidecar holding only the **newest** per-item breakdown per user: every name in the stash, the priced ones with their chaos value and the **unpriced ones at zero** (that is what lets the next diff tell an item that left the stash from one that only lost its price — `docs/bugs.md` B2). *Every* unpriced name goes in, not just the 100 the Net-Worth page lists: the names that cap drops are the thinly traded items the distinction is for. The file grows by those names and nothing else — a name and two numbers each. It exists so a container restart does not tear a hole into the series: without it the first point after every deploy would carry no delta. Its path is derived from the NDJSON path and cannot be set separately.
- **`networth-history-guard.json`** — the price brake's memory across restarts: running holds with the point they started at and were last seen at, the newest C:D rate, and remembered prices for names that are not in the last recorded point with a price (the others are taken back from the items sidecar at start; after a sidecar write that failed, or while the sidecar is left untouched, every name is kept here). After a failed sidecar write at a change in the set of stash tabs, it also names the sidecar entry that change dropped (`stale`), until the next sidecar write lands, so a start in between does not adopt it. A stretch in which the server was down counts like a point without a price: it neither proves nor ends a hold, so an update cannot release a suspicious price early. Written after a recorded point, and when a change in the set of stash tabs drops a breakdown, only when its content changed: a hold started or ended, a held item was there again (so at almost every point while a hold runs), a name entered or left the remembered prices, or the C:D rate moved. The rate's time alone is renewed only every half `POE_NETWORTH_GUARD_HOLD_MS`, so a restored rate may be up to half that window older than it really was. Its path is derived from the NDJSON path and cannot be set separately; its size is bounded by `POE_NETWORTH_GUARD_STATE_MAX_NAMES`.

None of the three files contains an account name or a POESESSID — only the local routing name from `POE_USERS` and item names.

**How often a point is recorded.** The auto-refresher offers one after every synced tab (i.e. roughly every 30s per user), but the history module throttles that down to **at most one point per minute per user**. There is nothing to schedule and no separate job. An offer is **refused while the refresher has not been past every live stash tab yet** — on a fresh install, or after a tab list that came back short pruned the stored tabs: until then the snapshot is a sum over a subset of the account, and recording it would put a dip into the curve that nothing afterwards can tell apart from a real one. Expect no points for up to one full round (tab count × `POE_NETWORTH_SYNC_INTERVAL_MS`) after the store is empty.

**How long it is kept, and how big it gets.** Retention is **15 days** — the longest selectable range (14d) plus a day of slack. At one point per minute that is ~21,600 lines per user over the full window, in practice a file of a few MB; the sidecar stays flat at roughly 130 KB per user because only the newest breakdown is ever kept. Retention is applied on load and, while running, about hourly: the file is only rewritten when there is actually something to drop.

A missing, empty, truncated or corrupt file never throws — unparsable lines are skipped individually, so a hard container kill costs at most the half-written tail point. But past points cannot be fetched again: deleting the series starts the curve over, so it belongs in a backup ([runbooks.md → Backup and restore](runbooks.md#backup-and-restore)). Losing only the sidecar costs the next point its item movers and its price guard check (both compare against the previous breakdown). If `/config` is not writable, the series degrades to memory-only instead of erroring once a minute.

**Two protections against a wrong chart** (both in `backend/v2/networth/price-guard.mjs`), because of a real incident: a 1-chaos divination card was valued at 174,039c for about an hour on an unchanged stack of one, which put a mountain worth twelve times the whole account into the trend and made the item panel blame a card that never moved.

- **A brake on implausible price jumps**, applied before a point is written. A jump has to clear **both** bars to count: the item's unit price grew by at least **20x**, *and* the resulting gain is at least **25 % of the previous total**. Ordinary market moves and cheap oddities therefore never trip it. The point is then recorded at the item's **previous** unit price and its total corrected by the same amount, with a `[networth]` warning naming the item, both prices and the share. Held prices are not held forever: after **6 hours** the brake lets go and accepts the new price as real (also logged). The brake guards the **history only** — the live Net Worth page keeps showing whatever the valuator produced, because a silent rewrite of the displayed net worth would hide the very bug this is meant to surface.

  **An arrival bar covers the item that has no previous price.** An item entering the stash cannot be compared with anything, so the jump bar cannot see it. One worth at least `POE_NETWORTH_GUARD_ARRIVAL_MIN_DIVINE` (default **20** divine) *and* at least `POE_NETWORTH_GUARD_SHARE` (25 %) of the previous total is recorded at no value until it has stood for the hold window (the same 6 hours), and then enters the series as stock arriving, visible in the event list rather than as an unexplained jump. The divine floor keeps a fresh account, where every drop is a large share of a small total, out of its reach; `0` switches the arrival bar off.
- **Removal of artefacts already on disk**, applied when the series is loaded. Points from before the brake existed are still in the file, and there they flatten everything real against the bottom of the value axis, which has to span the peak. A stretch is dropped only when it rises to at least **5x** the level right before it, comes back **down to within 2x** of that level afterwards, is **shorter than 6 hours**, and no stock movement explains the rise (a jump that stays up is someone getting richer, not a glitch). Each removal logs how many points went, the peak, the span and the level it returned to; the file is rewritten so the cleanup is permanent.

#### Farm sessions

A farm session answers one question: is what I am doing right now worth it. **Start farm session** in the History page's toolbar, or a hotkey daemon through `POST /daemon/session`, starts one. It is refused when the newest recorded point of this user is older than `POE_SESSION_BASELINE_MAX_AGE_MS` (the background sync is not running for them) and is unavailable when the background sync never started (`POE_NETWORTH_AUTOSYNC=0`, or the folder of the net-worth store could not be created at start).

A started session is **starting** until its baseline is read: the first point recorded after every live stash tab was read (or tried) once after the start, with its full item breakdown. The refresher reads that player's tabs first for it (a session round, under "Sync follows the game" above), so this takes about tab count × `POE_NETWORTH_SYNC_INTERVAL_MS`, divided by the player's share of the ticks (a half with two players who both play); the server's estimate is `about` in `GET /networth-sessions`. The estimate counts a folder tab (unique or map stash) as its 1+N steps once the refresher has walked it since the server started, and as one step before that, so it is too low until then; a player whose cookie expired gets no ticks and is left out of the shares. The newest point at the start is kept as a copy until the session ends: when no baseline point comes within `POE_SESSION_FINALIZE_MAX_MS`, or the session is ended before it came, or its baseline was read after the moment the session ended (a game session's end is dated back to when the game stopped), the session starts from that copy and says so (`baseline` `at-press`). A session that ends without a usable baseline and without a copy closes as "never confirmed" without figures.

**End farm session** (or `POST /daemon/session` again) stamps the end; **Discard** (after a confirmation in the browser) throws the running farm session away without a line in the list. The balance is **preliminary** until every live stash tab has been read (or tried) once after the end, again as a session round, and is then struck against the first point recorded after that and marked final. A session that does not get there within `POE_SESSION_FINALIZE_MAX_MS` is closed as "never confirmed" with the figures it has — at the next recorded point, at the next check (every 30 s), or the next time the History page loads its sessions; without a point from after the end it has no figures. A farm session never ends by itself: one that was forgotten keeps running, and its hourly figure falls accordingly.

A **game session** is the game evening around it, and runs by itself: it starts when the player's hotkey daemon reports the game running (game detection, `[presence] report_game`, on by default) and none runs, and ends once the daemon has reported the game not running for `POE_SESSION_GAME_GAP_MS` (10 min), dated to the moment the game stopped; a game restarted or crashed within that gap is the same evening. A daemon that cannot tell, stops reporting or was never installed changes nothing by itself: a gap that has begun still runs out (the game was closed, then the PC shut down), and a game session that saw no stop runs on and is closed as "never confirmed" `POE_SESSION_FINALIZE_MAX_MS` after the last report (a server start counts as one). When the game is reported running again after `POE_SESSION_GAME_GAP_MS` or longer without any report (the PC was shut down with the game running), the old session ends, dated to the last report, and a new one starts, so two evenings are never one session; a shorter silence (a network hiccup) is the same evening. Its balance works like a farm session's. A farm session started during a game session belongs to it and does not end with it. A game session has no Start or End button; while it runs, its card on the History page has a **Discard game session** (after a confirmation), which drops it without a line in the list and leaves its farm sessions in the list on their own. `POE_SESSION_AUTO_GAME=0` starts no game session; one that is already running still ends as described. The hotkey daemon's feed (`GET /daemon/events`) gets an event for every start, baseline, end and closing of both kinds. Game sessions and the session round are tested against a simulated daemon and refresher, not yet over a running game.

**What the page shows.** The list holds the running sessions, the ended ones waiting for their round and the newest `POE_SESSION_LIST_MAX` finished ones, newest first, with the kind (*Game session*, *Farm session*) and the state (*starting*, *running*, *preliminary*, *final*, *never confirmed*; *baseline at start* after it for an `at-press` baseline). A farm session started during a game session is drawn indented under it; one whose game session is not in the list (discarded, or older than the list holds) stands on its own, as does one started while no game session ran. The card shows the session picked in the list, else the running farm session, else the newest ended one still waiting for its final balance, else the running game session; for a starting session it says that the baseline comes with the next full read and the server's estimate in minutes, for an ended one when it is final, and after a farm session's end it asks for the loot still in the inventory to be stashed (only the stash is read). The sync line of every page says `Reading every tab once for the session (k of n).` while a session round runs and the sync runs normally (no cooldown, no expired or missing POESESSID).

The running farm session, else the running game session, also shows in the status line of every page (`Farm session 1:12 h · loot +3.4 div`, `Game session 3:05 h · …`; `baseline with the next full read` while it is starting). Sessions are per user (`ppt_user`) and cost no request: everything comes from points the history records anyway. Finished sessions keep their own summary and outlive the 15-day history retention, up to `POE_SESSIONS_KEEP` per user; the page lists the newest `POE_SESSION_LIST_MAX`. A tab added, removed or read for the first time during a session, or a league switch, marks it as no farming result (no hourly figure, and the status line shows no loot figure for it). What the figures mean: [pricing-logic.md](pricing-logic.md#what-a-farm-session-balance-means).

### The daemon's back channel

Besides `POST /item`, the server offers a hotkey daemon two more HTTP routes (`GET /daemon/events`, a long-poll feed of the cards that daemon posted, and `POST /daemon/heartbeat`, which carries its version, its game state and which of its parts work; `backend/v2/frontend/PROTOCOL.md`). They need nothing from you on the server side, keep everything in memory and send nothing to GGG or poe.ninja; reading the feed never queues a price check. They are for a daemon new enough to send `X-PPT-Daemon`; a daemon that does not send it is answered `400` there, and its `POST /item` is answered and handled as before.

Behind a reverse proxy only the read timeout matters: the server holds `GET /daemon/events` until something arrives, at most as long as the daemon asks (`hold_s` in its `config.toml`, 25 s by default) and never longer than `POE_DAEMON_POLL_MAX_HOLD_MS` (30 s), so a proxy read timeout above 30 s works (nginx's default of 60 s does).

The daemon uses the feed to show the price in the game, as a card over the game (the overlay) or as a desktop notification (README, "The price in the game"). Mixed versions work in both directions. An older daemon with this server: nothing changes. A newer daemon with an older server: the daemon writes one line per missing route to its journal (`journalctl --user -u poe-price-daemon`), keeps pricing, says `sent — the price shows in the browser only` in the game, and asks again every 10 minutes, so updating the server is enough. An older daemon that is still running after `git pull` keeps working as before until it is restarted.

What a daemon reports reaches the browser through `daemon-status`: the Price Check page names in its status line every part of the player's daemon that is not working (for example `overlay — no PySide6`), and the settings page shows the daemon's version under the latest release, with how to update it when it is behind. Without a heartbeat since the server started, the settings page says so. Once no daemon of the user has a fresh heartbeat (none for `POE_DAEMON_BEAT_STALE_MS` or three of the daemon's announced intervals, whichever is longer; checked every 30 s), the status line drops those parts and the settings page marks the version as the last report. The `[daemon] <user>: unknown -> playing (daemon <version>)` line in the server log marks each change of a user's presence (`playing`, `idle`, `unknown`). The net-worth refresher acts on it (see "Sync follows the game" under "Net-Worth-Tracker"); a change sends every user's sync status again.

When a player's daemon "does nothing", the client self-test (`daemon/selftest.sh`) and the table of its verdicts are in [runbooks.md → Client self-test](runbooks.md#client-self-test-daemonselftestsh). The league switch is [runbooks.md → League-start runbook](runbooks.md#league-start-runbook).

### Buyer whispers

A third route, `POST /daemon/whisper`, takes an incoming trade whisper from a hotkey daemon new enough to read the game's log (`client_log` in `[whispers]` of the player's `config.toml`; empty or missing: off): only a whisper that starts like a trade-site template (`trade_prefixes`), and with a pseudonym (`buyer 3`) instead of the buyer's name, which never leaves the game PC. The server reads the templates (English single and bulk, English single without a price, and single and bulk in German, French, Russian, Spanish and Portuguese; the templates are data in `backend/v2/whisper.mjs`; all but the English ones are from SlimTrade's patterns, not seen in a real log), values the goods with the same valuator as the Net Worth page (Faustus, then poe.ninja; never the trade API), and answers with a verdict on the player's own listed price: `below` or `above` the market outside `POE_WHISPER_LOW_RATIO` … `POE_WHISPER_HIGH_RATIO`, `fair` in between, or `not-compared` with the reason (docs/pricing-logic.md, "What a buyer-whisper verdict means"). A valuation that takes longer than `POE_WHISPER_PRICE_DEADLINE_MS` is answered `pending`, and the result follows through the daemon's feed and the page. The whisper must name the user's league; another league is not compared and costs no poe.ninja request. Item names are read with the server's language data, English and, once generated, German. A French, Russian, Spanish or Portuguese whisper has no data of its own: its item is compared only when its name is exactly one the loaded languages know, else it ends `not-compared` with `no-language-data`, its listed price still read.

Each entry also says whether the whisper's tab is a quad tab (`quad`, for the daemon's stash cell frame), from the stash tab type the net-worth refresher stores per tab in `networth-store.json` (`type`): no extra stash request. A tab stored before the type was kept says nothing until the refresher reads it again (one lap); the file keeps `schema_version: 2`.

Nothing is written to disk, and the server log gets one line per whisper with its kind, language and verdict, never its text, item or label. A failure is logged as `[whisper] valuation failed`, `[whisper] delivery failed` (handing the entry to the page or the daemon's feed) or `[whisper] handler failed`, at most one line a minute for each; the next line counts the ones left out, so a page that keeps saying "the check failed" always has a recent line behind it. The list on the Price Check page ("Buyer whispers (this session)") keeps `POE_WHISPER_KEEP` entries per user until the server restarts. A whisper the server cannot read is counted (`unparsed` in `daemon-status`, named in the page's status line) and dropped without its text. At most `POE_WHISPER_MAX_PER_MIN` whispers per user and minute are taken; more are answered 429. With `POE_PRICE_CHECK_DISABLED=1` whispers are read but not valued (`pricing-off`).

### Value grid

`GET /daemon/stash-grid` serves the daemon's value key: the user's stored tab list and, for one tab, where each priced item lies and what it is worth. The data is `cells` per tab in `networth-store.json`: cell, size, chaos value and name of every priced stash entry worth 1 c or more, the dearest 600 of the tab, and `u: true` on an entry whose own valuation is uncertain, the mark of the Net Worth page's Confidence column (the field is left out otherwise; which reason stays on that page, and a row there that folds several entries is marked when any of them is); an empty list for a tab whose items do not sit on cells (any type but normal, premium and quad). It is taken from the stash answer the refresher reads anyway, so the grid adds no request to GGG, poe.ninja or Faustus and no load on the stash API: a key press reads the store, and a tab's cells are as old as its last read. A tab stored before `cells` existed has none until the refresher reads it again (one lap), and the route says so (`not-read-since-update`); one stored before the tab type was kept is listed with `grid: false` until that read; the file keeps `schema_version: 2`. At most 60 requests per user and minute are taken (a fixed number, no setting); more are answered 429. Fields: [PROTOCOL.md](../backend/v2/frontend/PROTOCOL.md).
